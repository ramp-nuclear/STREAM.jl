# Relation to Python STREAM

STREAM.jl is a port of [Python STREAM](https://github.com/ramp-nuclear/STREAM), whose
documentation is at <https://ramp-nuclear.github.io/STREAM/>, and is meant to replace it.
The physics is the same: the same correlations, the same channel and plate equations, the
same point kinetics and decay heat. What changed is how a model is assembled
and solved.

## What is different in how models are built

Python STREAM builds a model from *calculations*, each computing fixed outputs from fixed
inputs. They are wired into a flow graph, from which Kirchhoff matrices are assembled, and
each calculation supplies its own Jacobian and mass vector. STREAM.jl builds the same model
from acausal components joined by connections (see [How a model is built](@ref)). The
assembly, the Jacobian, its sparsity pattern and the reduction of the differential-algebraic
system are derived symbolically by ModelingToolkit rather than written by hand.
[In Python STREAM's terms](@ref) maps each part of an aggregator to its ModelingToolkit
counterpart.

In practice this means:

- a component states its equations and nothing else, and joins any network without code to
  fit it there;
- the compiled equations can be read, before and after simplification, with `equations`,
  `unknowns` and `observed`;
- heat transfer and friction models are values handed to a channel, so a new correlation is a
  function, not a subclass;
- a dimension can stay symbolic as a design knob, and change between solves without a rebuild;
- every control action goes through one state machine whose transitions the solver locates at
  their exact instant.

## Deliberate departures

A few behaviours differ from Python on purpose:

- **Interpolation of the fission profile.** [`DecayHeat.Fissions`](@ref) interpolates the
  logarithm of a shut-down fission rate, where Python draws straight lines between samples
  and overshoots. [`DecayHeat.Linear`](@ref) restores Python's behaviour for a comparison.
- **Decay heat standards.** The tables are published standards and are not distributed with
  the package; see [Decay heat](@ref).
- **Power from outside fission.** [`PointKinetics`](@ref STREAM.Components.PointKinetics)
  takes an optional `power_input`, where Python needs a separate kinetics class.
- **Check valve opening.** The [`Flapper`](@ref STREAM.Components.Flapper) always opens along
  the smooth ramp ``3y^2 - 2y^3``, where Python defaults to a relaxation. The opening time is
  the same.
- **Equal decay rates.** [`DecayHeat.DoubleDecay`](@ref) switches to the equal-rate limit when
  its two rates nearly coincide, a case Python leaves unguarded.

## Where the physics is open

Where a modelling choice has no single right answer, STREAM.jl follows Python, so that the two
codes compare like for like:

- in [`HTC.RegimeDependent`](@ref), the laminar and natural convection branches read coolant
  properties at the bulk temperature and the turbulent branch at the film;
- Rohsenow's boiling constants are Python's, ``n = 1.26`` and ``C_{sf} = 0.011``. Textbooks
  give ``n = 1.0`` for water, and the source of Python's values has not been traced;
- each channel cell reads its saturation temperature at its outlet-side face.

## How the two are compared

The test suite holds STREAM.jl to Python STREAM in two ways:

- `test/test_integration.jl` ports each of Python's integration tests one for one. Most of
  them check a model against a closed-form solution, so the port checks the physics, not just
  agreement between the codes.
- `test/test_validation.jl` compares the results of whole models, steady and transient,
  against reference values generated by running Python STREAM.

`VALIDATION.md` in the repository lists each comparison and its status, and `GAPS.md` lists
what Python STREAM has that STREAM.jl does not yet, such as loss of coolant, cylindrical fuel
conduction and uncertainty quantification.
