# Phase 12.1: PipeGeometry Struct - Context

**Gathered:** 2026-03-14
**Status:** Ready for planning
**Why this exists:** Phase 10.5 was designed during Phase 10 and explicitly planned but was never inserted into ROADMAP.md. Phases 11 and 12 were built without the clean geometry API. Phase 12 VAL tests currently use physics-only assertions because the geometry mismatch between Julia (`π*Dh/2`) and Python STREAM (`heated_parts=(y, y)`) was 4.46× for MTR geometry, making quantitative comparison infeasible. This phase fixes that root cause.

<decisions>
## Implementation Decisions

### PipeGeometry struct fields

```julia
struct PipeGeometry
    L    ::Float64                   # pipe length [m]
    Dh   ::Float64                   # hydraulic diameter [m] — used for Re, Nu, h_tc, dP
    A    ::Float64                   # flow cross-section area [m²]
    heated_parts ::NTuple{2,Float64} # heated perimeter per face [m]: (left_face, right_face)
end
```

Derived property (not stored, computable): `heated_perimeter = sum(heated_parts)`.

**Why this set of fields:**
- `Dh` and `A` are what `_channel_base_eqs` needs — no change to that helper
- `heated_parts` is a 2-tuple mirroring Python STREAM's `EffectivePipe.heated_parts`; both faces explicit avoids the "divide total by 2" ambiguity
- `L` is included because it belongs to pipe geometry, not the component's discretization

**Fields NOT included (deferred to v0.4):**
- `wet_perimeter` (needed for CHF correlations only)
- `width`, `depth` (physical dimensions, needed for Elenbaas/Sudo-Kaminaga CHF)

### Factory functions

```julia
# Circular pipe — preserves existing behavior exactly
PipeGeometry(; L, D, A=π*D^2/4) = PipeGeometry(L, D, A, (π*D/2, π*D/2))

# Rectangular MTR channel — the fix
PipeGeometry(; L, Dh, A, y) = PipeGeometry(L, Dh, A, (y, y))
```

**Naming decision:** Use keyword-argument constructors (Julia multiple dispatch on kwargs), not module-namespaced factory methods like `PipeGeometry.circular(...)`. Julia idiom is multiple dispatch, not static methods.

**Why `y` (not `width` or `w`):** `y` matches the existing `HeatDiffusion` parameter name (`y=0.07`) and all planning docs. Consistency wins.

**Backward compatibility:** No backward-compat shim for old `(; name, n, L, D, A, g)` constructors. This is a clean break — the old API is wrong and all call sites are in tests we control. The Phase 10 decision to "not add backward compat shims" applies here too.

### How each channel uses heated_parts

**`ChannelAndContacts`** — two-sided, per-face:
```julia
# Left face:  geometry.heated_parts[1]
# Right face: geometry.heated_parts[2]
Dt(T[i]) ~ (mdot * cp * (T_up - T[i])
           + h_tc[i] * geometry.heated_parts[1] * dz * (thermal_left[i].T  - T[i])
           + h_tc[i] * geometry.heated_parts[2] * dz * (thermal_right[i].T - T[i]))
           / (rho * cp * A * dz)
thermal_left[i].Q_flow  ~ h_tc[i] * geometry.heated_parts[1] * dz * (thermal_left[i].T  - T[i])
thermal_right[i].Q_flow ~ h_tc[i] * geometry.heated_parts[2] * dz * (thermal_right[i].T - T[i])
```

**`Channel`** — single thermal port, total perimeter:
```julia
# Uses sum(heated_parts) — for circular: π*D/2 + π*D/2 = π*D (same as current π*Dh)
Dt(T[i]) ~ (mdot * cp * (T_up - T[i])
           + h_tc[i] * sum(geometry.heated_parts) * dz * (thermal.T - T[i]))
           / (rho * cp * A * dz)
q_wall[i] ~ thermal.Q_flow / n
```

**`ChannelHeatFlux`** — scalar T_wall, total perimeter:
```julia
# Uses sum(heated_parts) — for circular: π*D (same as current π*Dh)
Dt(T[i]) ~ (mdot * cp * (T_up - T[i])
           + h_tc[i] * sum(geometry.heated_parts) * dz * (T_wall_p - T[i]))
           / (rho * cp * A * dz)
q_wall[i] ~ h_tc[i] * sum(geometry.heated_parts) * dz * (T_wall_p - T[i])
```

### New constructor signatures

```julia
function Channel(; name, n::Int, geometry::PipeGeometry, g=0.0)
function ChannelHeatFlux(; name, n::Int, geometry::PipeGeometry, g=0.0, T_wall)
function ChannelAndContacts(; name, n::Int, geometry::PipeGeometry, g=0.0)
```

`geometry.L` replaces the `L` kwarg. `geometry.Dh` replaces `D`. `geometry.A` replaces `A`. The internal `dz = geometry.L / n`.

### THERM-03 test under the new API

THERM-03 compares one-sided ChannelAndContacts vs ChannelHeatFlux. With PipeGeometry, the "equalize perimeters" invariant becomes:

```
CAC one-sided left face: geometry_cac.heated_parts[1]
CHF total:               sum(geometry_chf.heated_parts)
```

For them to match: `geometry_cac.heated_parts[1] == sum(geometry_chf.heated_parts)`.

Simplest: use `PipeGeometry(; L, D=2*D_chf, A=A_ch)` for CAC (circular with D=2×D_chf).
Then `heated_parts[1] = π*(2*D_chf)/2 = π*D_chf = sum(π*D_chf/2, π*D_chf/2)`. ✓

Same invariant as Phase 10's `D_cac = 2 * D_chf`, just expressed via PipeGeometry.

### generate_mtr_reference.py update

Change `pipe_ch` from circular to rectangular MTR geometry:

```python
# Before (wrong for MTR — circular pipe):
pipe_ch = EffectivePipe(
    length=LZ,
    heated_perimeter=np.pi * D_H,
    wet_perimeter=np.pi * D_H,
    area=np.pi * D_H**2 / 4,
    heated_parts=(np.pi * D_H / 2, np.pi * D_H / 2),
    width=D_H,
)

# After (correct rectangular MTR channel):
pipe_ch = EffectivePipe(
    length=LZ,
    heated_perimeter=2 * Y_LEN,          # 2 * 0.07 = 0.14 m
    wet_perimeter=np.pi * D_H,           # hydraulic: unchanged (D_H=0.01)
    area=np.pi * D_H**2 / 4,             # flow area: unchanged (= 7.85e-5 m²)
    heated_parts=(Y_LEN, Y_LEN),         # 0.07 m per face
    width=Y_LEN,                         # plate width (MTR convention)
)
```

Note: `area = np.pi * D_H**2 / 4 = 7.85e-5` is kept — this is the HYDRAULIC equivalent area for pressure drop, matching `A=7.85e-5` in Julia. This is correct: the rectangular channel's actual flow area is `depth * width` but we use the circular hydraulic equivalent throughout for Darcy-Weisbach.

<pitfalls>
## Known Pitfalls to Avoid

### Pitfall 1: `_channel_base_eqs` does NOT need geometry

`_channel_base_eqs` takes `Dh, A, L, g_acc, dz` as plain scalars. The caller (channel constructor) extracts them from `geometry`. Do not refactor `_channel_base_eqs` itself — it is a low-level helper and the scalar interface is correct.

### Pitfall 2: `sum(heated_parts)` for Channel/CHF, NOT `heated_parts[1]`

`Channel` and `ChannelHeatFlux` have a single thermal coupling (one T_wall, wraps full perimeter). They use `sum(geometry.heated_parts)` = total heated perimeter. Only `ChannelAndContacts` uses per-face indexing.

### Pitfall 3: Factory function disambiguation

Two `PipeGeometry` constructors:
- Circular: `PipeGeometry(; L, D, A=π*D^2/4)` — has kwarg `D`
- Rectangular: `PipeGeometry(; L, Dh, A, y)` — has kwarg `y`

Must be different enough that Julia dispatch can distinguish. If ambiguous, use explicit inner constructor for the struct and named outer constructors `circular_pipe(L, D, A)` / `rectangular_channel(L, Dh, A, y)`. Decide during planning.

### Pitfall 4: VAL reference constants checkpoint

The Python script must be run AFTER the Julia refactor is committed (to ensure the Python side matches the new Julia geometry). The new reference constants should be hardcoded into runtests.jl in a separate commit from the refactor. Plan should include an explicit checkpoint/wave break here.

### Pitfall 5: THERM-03 CAC adiabatic test (CHAN-03)

THERM-03 currently verifies both: (1) one-sided CAC matches CHF T_outlet within 0.1%, and (2) unconnected right side has Q_flow=0. Both must still pass after PipeGeometry. The `D_cac = 2 * D_chf` invariant becomes `geometry_cac.heated_parts[1] == sum(geometry_chf.heated_parts)` — see Decisions section.

### Pitfall 6: STATE.md stale entries

Three Key Decisions entries explicitly reference `π*Dh/2`. They must be updated after implementation — see Decisions section. Failure to update leads to future confusion.

</pitfalls>
