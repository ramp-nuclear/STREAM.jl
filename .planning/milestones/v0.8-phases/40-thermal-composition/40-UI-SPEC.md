## ThermalPort Handle Contract

This section defines the visual and interaction contract for ThermalPort handles added in Phase 40.

### Handle Appearance

| Property | FlowPort (existing) | ThermalPort (new) |
|----------|--------------------|--------------------|
| Shape | Circle | Diamond (45-degree rotated square) |
| Fill color | `var(--background)` white | #f59e0b amber-500 |
| Border | 1px solid `var(--foreground)` | 1px solid #d97706 amber-600 |
| Size | 8x8px | 10x10px (slightly larger to accommodate diamond rotation) |

Rationale for diamond shape: Provides instant visual differentiation from FlowPort circles without relying solely on color. Accessible to colorblind users. Achieved via CSS `transform: rotate(45deg)` on the Handle element with `borderRadius: 0` override.

### Handle Placement (from CONTEXT.md D-02)

| Component | ThermalPort | Position | ReactFlow Handle type |
|-----------|-------------|----------|-----------------------|
| ChannelAndContacts | thermal_left | Top edge | target |
| ChannelAndContacts | thermal_right | Bottom edge | source |
| HeatDiffusion | thermal_left | Left edge | target |
| HeatDiffusion | thermal_right | Right edge | source |
| ConstantTemperature | thermal | Left edge | target |

Handle type assignment rule: left/top = `target`, right/bottom = `source`. This ensures every valid ThermalPort-to-ThermalPort connection has exactly one source and one target endpoint, which ReactFlow requires for edge drawing.

### Handle Count Rule (from CONTEXT.md D-01, D-04)

One handle per ThermalPort entry in the registry, regardless of `n` or `nz` parameter value. The GUI abstracts away per-cell detail. The `array: true` field is consumed only by the code generator.

### Handle Data Attribute

Every Handle element (both FlowPort and ThermalPort) carries `data-port-type` attribute:
- FlowPort handles: `data-port-type="FlowPort"`
- ThermalPort handles: `data-port-type="ThermalPort"`

This supports the `isValidConnection` callback (see Connection Enforcement below).

## ThermalPort Edge Contract

### Edge Appearance

| Property | FlowPort edges (existing) | ThermalPort edges (new) |
|----------|--------------------------|-------------------------|
| Stroke color | Default (var(--foreground) or ReactFlow default) | #f59e0b amber-500 |
| Stroke style | Solid | Dashed (strokeDasharray: "6 3") |
| Stroke width | 2px | 2px |
| Edge type | smoothstep | smoothstep |

Rationale for dashed style: Provides a second visual cue (in addition to color) that distinguishes thermal connections from hydraulic connections. Reinforces the conceptual difference -- thermal connections represent heat transfer paths, not fluid flow paths.

### Edge Style Application

Edge style is set at creation time in the store's `addEdge` function. When a new edge is created, look up the port types of both connected handles via registry. If both are ThermalPort, apply:
```
{ stroke: "#f59e0b", strokeDasharray: "6 3" }
```

## Connection Enforcement Contract (from CONTEXT.md D-05, D-06)

### isValidConnection Rules

The `isValidConnection` callback on `<ReactFlow>` enforces:

1. Both source and target must be non-null
2. Both sourceHandle and targetHandle must be non-null
3. Source port type must equal target port type (FlowPort-to-FlowPort OR ThermalPort-to-ThermalPort)
4. Cross-type connections (FlowPort-to-ThermalPort) are blocked -- the edge cannot be dropped

Port type is determined via registry lookup: find the node's `componentId` from store, look up the port definition in the registry by handle name, read the `type` field.

## Code Generation Visual Contract

Phase 40 does not add new visible UI panels or controls. The code generation changes are internal to `codeGenerator.ts` and affect the text content of the existing code preview panel.

### Generated Code Format Changes

When thermal edges exist on the canvas, the code preview shows:

1. A `# Thermal assembly (auto-detected: {pattern})` comment before each helper call
2. `@named assembly_N = {helper}(args...)` declaration
3. Hydraulic `connect()` calls using dotted assembly paths: `assembly_1.cac_1.inlet`
4. `compose_systems(assembly_1, ...; connections=eqs, name=:sys)` instead of `ODESystem`

When no thermal edges exist, the code preview is unchanged from Phase 36 format.

When thermal wiring is unrecognized, emit:
```
# TODO: verify thermal wiring
```

### nz/n Mismatch Warning

When a HeatDiffusion node (nz=M) is connected to a ChannelAndContacts node (n=N) and M != N, the code generator emits:
```
# NOTE: HeatDiffusion nz (M) must equal ChannelAndContacts n (N) for this helper to work correctly
```

## Implementation Boundaries

### In Scope for Phase 40
- ThermalPort handle rendering on StreamNode (ChannelAndContacts, HeatDiffusion, ConstantTemperature)
- Diamond shape + amber color for ThermalPort handles
- `data-port-type` attribute on all Handle elements (FlowPort and ThermalPort)
- `isValidConnection` port-type enforcement in CanvasPanel
- Amber dashed edge styling for ThermalPort connections (set at edge creation time)
- Thermal topology detection in codeGenerator (symmetric_plate, plate, one_sided_connection, fallback)
- compose_systems code emission when thermal assemblies detected
- nz/n mismatch warning comment in generated code

### Out of Scope
- Per-cell ThermalPort handles (deferred -- always one handle per side)
- Layered canvas with hydraulic/thermal toggling (Phase 41)
- New VALD rules for ThermalPorts (D-11: unconnected thermal = valid adiabatic)
- Dark mode
- New shadcn primitives
