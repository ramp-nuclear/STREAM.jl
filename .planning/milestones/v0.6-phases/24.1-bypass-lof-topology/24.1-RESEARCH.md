## Summary

Phase 24.1 replaces the series-loop LOF model from Phase 24 with a physically correct bypass topology. The core changes are: (1) add a `L/A * Dt(port_in.mdot)` inertial term to `_channel_base_eqs` in `channel.jl`; (2) add a `build_loop_lof_bypass()` function in `examples.jl` that wires a 4-node parallel network with real junctions; (3) replace `test/test_loss_of_flow.jl` with new tests targeting the bypass topology; (4) export the new builder from `STREAM.jl`.

All implementation patterns are already present in the codebase. The momentum inertia term is identical to the standalone `Inertia` component (`misc.jl`). The `Flapper` component, `HeatExchanger`, `Resistor`, and `Pump`+`Inertia` patterns all exist and are tested.

**Primary recommendation:** Modify `_channel_base_eqs` to add the inertial pressure term, then build the 4-node bypass topology in `build_loop_lof_bypass()` following the `build_cube` junction pattern.

## Architecture Patterns

### Channel Momentum Inertia Addition

The `_channel_base_eqs` helper in `src/components/channel.jl` (lines 125-165) currently writes:

```julia
push!(eqs, dP ~ f_ch * (port_in.mdot * abs(port_in.mdot) / (2 * rho_water(T[i_mid]) * A^2)) * (L / Dh)
             + rho_water(T[i_mid]) * g_acc * L)
```

The required addition (one extra term at the end):

```julia
push!(eqs, dP ~ f_ch * (port_in.mdot * abs(port_in.mdot) / (2 * rho_water(T[i_mid]) * A^2)) * (L / Dh)
             + rho_water(T[i_mid]) * g_acc * L
             + (L / A) * Dt(port_in.mdot))
```

**Sign convention:** identical to `Inertia` in `misc.jl` line 30:
```julia
port_in.P - port_out.P ~ L_over_A * Dt(port_in.mdot)
```
which when rearranged into dP form (where `port_out.P - port_in.P ~ -dP`) gives `dP` includes `+(L/A)*Dt(port_in.mdot)`.

**MTK auto-promotion:** MTK automatically promotes `port_in.mdot` to a differential state when `Dt(port_in.mdot)` appears, identical to how `Inertia` works. No explicit `vars` entry needed. This applies to Channel, ChannelHeatFlux, and ChannelAndContacts simultaneously since all three call `_channel_base_eqs`.

**`Dt` operator:** `_channel_base_eqs` does not currently declare a local `Dt`. It must be passed in or declared inside the function. Checking the call sites: `ChannelHeatFlux` and `ChannelAndContacts` both declare `Dt = Differential(t)` locally but do NOT pass it to `_channel_base_eqs`. The simplest fix is to declare `Dt = Differential(t)` inside `_channel_base_eqs` itself (since `t` is module-level from MTK).

### Bypass Topology Wiring (4-node parallel network)

The `build_cube` function (lines 273-316 of `examples.jl`) demonstrates MTK's variadic `connect()` for multi-way junctions. The bypass topology uses the same pattern.

**Node mapping to MTK connect:**
- Node A (junction): `pump_ine.port_out`, `ch.port_in`, `flapper.port_in` — 3-way connect
- Node B (junction): `ch.port_out`, `ret.port_in` — 2-way connect (just `connect(ch.port_out, ret.port_in)`)
- Node C (junction): `ret.port_out`, `flapper.port_out`, `ext_res.port_in` — 3-way connect
- Node D (junction): `ext_res.port_out`, `hx.port_in`; `hx.port_out`, `pump.port_in` — series

**Component naming convention (following build_loop_lof):**
- `pump` — Pump(0.0)
- `ine` — Inertia(L_over_A=...)
- `ch` — ChannelHeatFlux (heated, downward A→B)
- `ret` — Channel (unheated return pipe, B→C)
- `flapper` — Flapper
- `ext_res` — Resistor (high R, C→D)
- `hx` — HeatExchanger (temperature reset)

**Junction wiring:**
```julia
# Node A: pump+ine output → channel input AND flapper input
connect(ine.port_out, ch.port_in, flapper.port_in),
# Node B: channel output → return pipe input (simple 2-way)
connect(ch.port_out, ret.port_in),
# Node C: return pipe output → flapper output → external resistor input
connect(ret.port_out, flapper.port_out, ext_res.port_in),
# D→A pump branch (series)
connect(pump.port_out, ine.port_in),
connect(hx.port_out, pump.port_in),
connect(ext_res.port_out, hx.port_in),
```

**Important MTK acausal note:** In MTK's acausal hydraulic semantics, `connect()` enforces:
- `sum(mdot) = 0` at the junction
- All connected pressures are equal
- `instream()` mixes temperatures by mass flow

For the 3-way junction at A: `ine.port_out.mdot + ch.port_in.mdot + flapper.port_in.mdot = 0`. Since `ine.port_out.mdot < 0` (flow OUT of Inertia), `ch.port_in.mdot` and `flapper.port_in.mdot` will be positive when receiving flow. The convention is consistent — MTK handles the sign algebra.

### Gravity Sign Convention

From CONTEXT.md: ChannelHeatFlux goes A→B (nominally downward). In the channel dP equation:
```
dP ~ friction + rho * g_acc * L
port_out.P - port_in.P ~ -dP
```

For **downward flow** (A is top, B is bottom, flow going down):
- Static head: P_B > P_A (bottom has higher pressure) — so `port_out.P > port_in.P`, meaning `port_out.P - port_in.P > 0`, meaning `-dP > 0`, meaning `dP < 0`.
- To get `dP < 0` when flowing down: `g_acc` must be **negative** (gravity assists downward flow).

From `test_channel.jl` and `build_loop_vertical`: the convention uses `g_acc = 9.80665` for an **upward** channel (gravity opposes upward flow, adding to dP). For a downward channel (gravity assists), `g_acc = -9.80665`.

**In build_loop_lof (Phase 24):** `g_acc_ch = 9.80665` was used with the channel described as "upward channel orientation; gravity opposes positive flow." In Phase 24 the channel was the upward leg (flow goes up).

**In bypass topology:** ChannelHeatFlux goes A→B (nominally downward). Therefore `g_acc` for the channel should be **negative** (e.g., `g_acc_ch = -9.80665`) so gravity assists downward flow and opposes upward NC flow. The return pipe (Channel, B→C, nominally upward) should have `g_acc = +9.80665` so gravity opposes upward flow in nominal operation and assists downward NC flow.

**Verify:** For NC equilibrium the buoyancy loop must produce net positive driving pressure for the NC direction. Buoyancy drive: hot channel (low rho) goes up in NC, cold return pipe (high rho) goes down in NC. With the above sign assignment: the channel `dP` in NC (reversed, upward flow) has `g_acc = -9.80665` — the gravity term becomes `-rho_hot * g * L` which adds pressure drive for upward flow (since it subtracts from resistance). The return pipe in NC (reversed, downward flow, so negative mdot) has `g_acc = +9.80665` — the gravity term `+rho_cold * g * L` also contributes to driving. This is the correct thermosyphon physics.

### IC Strategy for Bypass Topology

Phase 24's IC strategy required a reference loop (no Flapper/Inertia) for KINSOL SS, then transferring T cells and mdot to the LOF system. The bypass topology has two additional unknowns (return pipe T cells, flapper state). The IC strategy needs updating:

1. Build a **reference forced-flow loop** to get SS mdot and T cells: use `ChannelHeatFlux` (downward, dP matching forced flow) alone without Flapper/Inertia (same KINSOL-friendly approach).
2. Transfer: `ch.T[i]` cells from SS, `ine.port_in.mdot` = mdot_ss for the pump+inertia branch, `flapper.T_open = 1e30` (sentinel), `ret.T[i]` = T_inlet (return pipe starts at inlet temperature since it's a cold-leg return).
3. The Flapper starts fully closed (`T_open = 1e30`), so all flow goes through the long path initially.

**Fully determined system:** The bypass topology has more components than build_loop_lof. Check whether `mtkcompile(sys; fully_determined=false)` is still needed. Since Flapper's `ref_mdot` must be wired externally (and IS wired in the topology: `flapper.ref_mdot ~ ine.port_in.mdot`), the system should be fully determined. Test LOF-01 verifies `length(equations(ssys)) == length(unknowns(ssys))`.

**Assessment:**
- `Pump(0.0) + Inertia` pattern is what Phase 24 used. State.md confirms: `[v0.6 FLAP-06]: Callable Pump(f(t)) cannot be used in same ODEProblem as Flapper (SymbolicContinuousCallback)`. This is a hard constraint — callable Pump breaks with Flapper's event system.

### Return Pipe (Channel, unheated)

The return pipe B→C uses `Channel` (not `ChannelHeatFlux`) with:
- `T_wall = T_inlet` equivalent — but since there's no heat input, the `thermal` port just needs a boundary condition. Options:
  1. Use `Channel` and wire `ret.thermal.T ~ T_inlet` (the channel has a ThermalPort).
  2. Set `h_tc` effectively to 0 by pinning thermal.T to the fluid temperature.
- Actually, `Channel` requires `thermal.T` to be pinned. For an unheated pipe the simplest approach is `ret.thermal.T ~ T_inlet` (cold wall). This will have negligible effect for a short return pipe but is physically reasonable.
- Alternative: use a `Channel` with very low `g_acc` for the return pipe and pin thermal T. Or use a `Friction` + `Gravity` combination.

**Recommended:** Use `Channel` for the return pipe (it already handles sign-correct upwind T advection, gravity, friction). Wire `ret.thermal.T ~ T_inlet` as the thermal BC. This keeps the return pipe at approximately inlet temperature, which is correct for a cold-leg return.

### Energy Balance Test Formula

From the existing test (VAL-01/VAL-02), the energy balance formula is:
```
Q_meas = |mdot| * cp_water(T_inlet) * |T_max_cells - T_inlet|
```
where `T_max_cells = maximum(T[1..n])` selects the correct outlet in both flow directions. This formula remains valid for the bypass topology since the heated channel is still `ChannelHeatFlux` with the same `q_wall[i]` observables.

**Checkpoints:** Same as Phase 24 (5 evenly-spaced checkpoints for VAL-01, last 10% window for VAL-02).

### Mdot Observable in Bypass Topology

In the series LOF, `ssys.ine.port_in.mdot` gave the unique system mdot. In the bypass topology, the channel and flapper carry different mdots. Tests should observe `ssys.ch.port_in.mdot` (channel branch) for LOF-03 (flow reversal) and VAL-01/02. The inertia mdot `ssys.ine.port_in.mdot` is the pump branch mdot (D→A), which is different from the channel mdot once the flapper opens.

**LOF-02 Flapper threshold:** Flapper fires when `ine.port_in.mdot` drops to threshold (since `ref_mdot ~ ine.port_in.mdot`). LOF-02 should check `flapper.T_open < 1e10`.

**LOF-03 flow reversal:** Check `ch.port_in.mdot` (channel branch) crosses zero and goes negative.

### Analytical NC Estimate (VAL-02)

From CONTEXT.md:
```
mdot_nc ~ sqrt((rho_cold - rho_hot) * g * H * A^2 / (f * L / Dh))
```
At NC equilibrium: buoyancy pressure = friction pressure.
- `H` = channel height `L_ch`
- `rho_cold` = rho at T_inlet, `rho_hot` = rho at average NC channel temperature
- `f` = Blasius friction at NC Re
- `A` = channel cross-sectional area
- `Dh` = hydraulic diameter

Since NC mdot is much lower than forced flow, the NC channel temperature rise will be higher. The iteration for this estimate requires assuming an NC mdot, computing T_outlet = T_inlet + Q_wall / (mdot * cp), computing rho_hot, then checking balance. The 20% tolerance accommodates this implicit iteration being approximated.

## Common Pitfalls

### Pitfall 1: Dt operator not in scope inside _channel_base_eqs
**What goes wrong:** `_channel_base_eqs` currently has no `Dt = Differential(t)` declaration. Adding `Dt(port_in.mdot)` without declaring `Dt` locally causes a `UndefVarError`.
**Why it happens:** The function is a helper called from multiple component constructors — each caller declares their own `Dt`, but does not pass it as an argument.
**How to avoid:** Add `Dt = Differential(t)` at the top of `_channel_base_eqs` (before the loop). `t` is module-level from MTK.
**Warning signs:** `UndefVarError: Dt not defined` during package load.

### Pitfall 2: Inertial term causes fully_determined=false requirement
**What goes wrong:** Adding `Dt(port_in.mdot)` to `_channel_base_eqs` promotes `port_in.mdot` as a differential state. MTK's structural analysis may flag this differently than before and require `fully_determined=false` at compile time.
**Why it happens:** MTK counts equations vs unknowns before structural simplification; promoting a new state variable may temporarily unbalance the count.
**How to avoid:** If `mtkcompile(sys)` errors with a "structurally singular" or "overdetermined" message, switch to `mtkcompile(sys; fully_determined=false)`. The Phase 24 `build_loop_lof` already uses `fully_determined=false` — the bypass topology should do the same.
**Warning signs:** `MTK structural analysis error` or `system is overdetermined` during compile.

### Pitfall 3: Backwards Flapper port wiring at junction C
**What goes wrong:** Flapper is bidirectional (A↔C), but MTK ports have orientation. If `flapper.port_in` is wired to C and `flapper.port_out` to A, the convention is reversed from nominal (nominal flow is A→flapper→C).
**Why it happens:** In bypass mode the Flapper short-circuits A and C; nominal flow direction is from A. Using `connect(ret.port_out, flapper.port_out, ext_res.port_in)` puts `flapper.port_out` at C. Since the Flapper equation uses `port_in.P - port_out.P ~ R * port_in.mdot`, this defines positive mdot as A→C through the flapper, which is correct for bypass (from A toward C).
**How to avoid:** Confirm junction-C wiring matches expected nominal bypass direction. Test LOF-02 (flapper fires) and LOF-03 (reversal) together validate this.
**Warning signs:** Flapper fires at t=0 (wrong direction detection) or flapper never opens.

### Pitfall 4: Return pipe gravity sign
**What goes wrong:** If the return pipe uses the same positive `g_acc` as the forced-flow upward channel in Phase 24, the gravity term is reversed and NC equilibrium won't be reached.
**Why it happens:** Phase 24's channel was the upward leg; Phase 24.1's channel is the downward leg. The gravity sign must flip.
**How to avoid:** ChannelHeatFlux (downward, A→B): `g = -9.80665`. Return Channel (upward, B→C): `g = +9.80665`. Check: in NC (reversed), channel flows upward (g_acc = -9.80665 helps it) and return flows downward (g_acc = +9.80665 helps it). Net buoyancy drive = `(rho_cold - rho_hot) * g * H > 0`. Correct.
**Warning signs:** NC equilibrium mdot has wrong sign or LOF-03 fails.

### Pitfall 5: IC for return pipe T cells
**What goes wrong:** If `ret.T[i]` initial conditions are left at the default 600 K, the solver may diverge during the transient startup or produce physically wrong temperatures in the NC phase.
**Why it happens:** The default variable IC in `Channel` is `fill(600.0, n)` — well above T_inlet.
**How to avoid:** In the IC op vector, set all `ret.T[i] => T_inlet` (313.15 K). The return pipe carries cooled water at T_inlet in forced-flow SS.
**Warning signs:** Anomalous T spike in return pipe at t=0, or energy balance failure at first checkpoint (VAL-01).

### Pitfall 6: Flapper ref_mdot wiring in build_loop_lof_bypass
**What goes wrong:** Forgetting to wire `flapper.ref_mdot ~ ine.port_in.mdot` causes mtkcompile to error (under-determined system — ref_mdot has no equation).
**Why it happens:** Flapper's `ref_mdot` is intentionally un-equated inside the component (FLAP-04 design).
**How to avoid:** Include `flapper.ref_mdot ~ ine.port_in.mdot` in the connections list, identical to Phase 24's `build_loop_lof`.
**Warning signs:** `MTK: system is under-determined` error during mtkcompile.

## Open Questions

1. **Does adding `Dt(port_in.mdot)` to `_channel_base_eqs` break existing tests for Channel/ChannelAndContacts?**
   - What we know: The `Inertia` standalone component uses the same term with `vars=[]`. Existing steady-state tests solve `SteadyStateProblem` where time-derivatives are zero — so the inertial term vanishes at SS and won't change SS results.
   - What's unclear: Whether MTK's `SteadyStateProblem` correctly handles the promoted `port_in.mdot` differential state (it should set `Dt(mdot) = 0`).
   - Recommendation: Run existing channel test suite after the `_channel_base_eqs` change. If `test_channel.jl` or `test_solvers.jl` fail, investigate whether a `Dt = 0` steady-state constraint is missing.

2. **Gravity sign for ChannelHeatFlux (downward, A→B) — exact value to use?**
   - What we know: Phase 24 used `g_acc_ch = +9.80665` for an "upward channel." The bypass topology's heated channel goes downward.
   - What's unclear: Whether `g = -9.80665` is the correct parameter sign for a downward channel in the dP equation `dP ~ friction + rho * g_acc * L`.
   - Recommendation: Verify by checking `test_channel.jl` gravity tests. The `build_loop_vertical` uses `g = +9.80665` for the channel (upward leg) and `Gravity(H=H)` for the return. For the bypass downward channel, `g = -9.80665` should give `dP_gravity = rho * (-9.80665) * L < 0`, meaning gravity assists downward flow (pressure at bottom > top). This is physically correct.

3. **How long must the transient simulation run to reach NC equilibrium?**
   - What we know: Phase 24 used 300 s for the series loop. The bypass topology has faster channel mdot drop (bypass path drains flow quickly), but NC establishment timescale depends on thermal inertia.
   - What's unclear: Whether 300 s is sufficient for the bypass topology to reach quasi-steady NC.
   - Recommendation: Start with 300 s (same as Phase 24). If VAL-02 (NC energy balance) fails because the system hasn't equilibrated, extend to 500 s or 600 s. The NC timescale is `(rho * A * L * cp) / (h_tc * perimeter * dz)` ≈ thermal relaxation time of the channel.
