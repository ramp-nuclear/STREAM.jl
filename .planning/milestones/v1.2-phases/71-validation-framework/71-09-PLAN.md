<objective>
Add the Validation tab to BottomPanel and the panel body that lists ValidationResult entries with click-to-focus AND fix-action buttons per D-01, D-04, D-05, D-14. Switch BottomPanel's Tabs to controlled so Plan 12's export gate and Plan 10's statusbar chip can programmatically focus the tab. Implement BOTH event-driven filters that D-05 requires (severity from statusbar chips, per-node from NodeContextMenu) AND the three-kind FixAction button rendering per §3.9 (lossless-sync / value-transfer-picker / navigation-only).

Purpose: this is THE place per §3.9 — every validator result surfaces here. The panel must be available even when count=0 (D-04 always-visible tab). D-05's "pre-filter by that severity" on statusbar chip click and "scrolls to entries for this nodeId" on right-click are locked decisions — both filters MUST land in this plan because no other plan owns the ValidationPanel listener surface. D-14's fix-action buttons (the FixAction discriminated union from Plan 01, emitted by Plans 05 and 06) MUST also land here because the ValidationPanel row is the ONLY surface that renders them — §3.9 line 780 explicitly states "the fix action lives ONLY on the validation panel entry."

Output: ValidationPanel.tsx component (list + sort + click-to-focus + empty state + severity filter listener + node filter listener + fix-action button rendering for all three kinds) + BottomPanel.tsx modifications to add the second tab and controlled state.

The intent was scheduling-only — BottomPanel UI does not actually depend on rule logic; the panel renders whatever `validationResults` contains, including the empty array Plan 01 ships. Wave dropped to **2** to allow UI build in parallel with rule files. The FixAction discriminated union is defined in Plan 01 (Wave 1) so the fix-action button TypeScript compiles cleanly even before Plans 05/06 ship the producing rules; the buttons render literally nothing for results whose `fixAction` is undefined. Plan 11 still serializes after Plan 09 + Plan 10 (it consumes both surfaces) and now sits at Wave 3.

    **Subscribe to:**
      - validationResults: ValidationResult[] from useStore.

    **Local filter state (D-05 locked behavior):**
      - `const [severityFilter, setSeverityFilter] = useState<'error' | 'warning' | 'info' | null>(null);`
      - `const [nodeFilter, setNodeFilter] = useState<string | null>(null);`

    **Window event listeners (single useEffect with proper teardown):**
      - `'stream:validation-filter'` — read `event.detail.severity` (typed as `'error' | 'warning' | 'info'`); call `setSeverityFilter(detail.severity)`. Also clear any active node filter (`setNodeFilter(null)`) so the two filters are mutually exclusive — clicking a statusbar chip is the user saying "show me this severity, drop the per-node lens". The filter REPLACES the previous one (subsequent clicks on a different chip switch the filter — they do not stack).
      - `'stream:validation-filter-node'` — read `event.detail.nodeId` (string); call `setNodeFilter(detail.nodeId)`. Also clear `setSeverityFilter(null)` for the same mutual-exclusion reason.
      - Tear down both listeners on unmount.

    **Filter pipeline (applied to validationResults in order):**
      1. Start with `validationResults`.
      2. If `severityFilter !== null`: keep only `r => r.severity === severityFilter`.
      3. If `nodeFilter !== null`: keep only results whose `targets` array contains at least one target T where (`T.kind === 'node' && T.nodeId === nodeFilter`) OR (`T.kind === 'port' && T.nodeId === nodeFilter`) OR (`T.kind === 'field' && T.nodeId === nodeFilter`). Edge targets matching by source/target endpoint are deferred to Plan 11's NodeContextMenu predicate (the menu does not dispatch for edge-only matches).
      4. Sort: severity-then-validatorId using rank Map `{ error: 0, warning: 1, info: 2 }`.

    **Filter-banner UI:** when any filter is active, render a one-line banner ABOVE the list:
      - For severity filter: `Showing only <severity> results · <count of N>  [Clear filter]`
      - For node filter: `Filtered to <nodeId> · <count of N>  [Clear filter]`
      - The "Clear filter" button (shadcn Button variant="ghost" size="sm") calls `setSeverityFilter(null); setNodeFilter(null);`.

    **Empty state:** when the filtered array length === 0:
      - If no filter active: render the centered terse string `"No issues."` (D-04 + engineering voice). Wrap in a div with `text-muted-foreground text-sm p-4 text-center`.
      - If a filter is active: render `"No results match the active filter."` with the same Clear filter button so the user can recover. (Engineering voice — terse, actionable.)

    Add the following conditional block in the row JSX, AFTER the description text and BEFORE the validator-id chip. The block renders nothing when `result.fixAction === undefined`. When defined, branch on `result.fixAction.kind`:

    ```tsx
    {result.fixAction && (() => {
      const fa = result.fixAction;
      const stop = (e: React.MouseEvent) => e.stopPropagation();

      if (fa.kind === 'lossless-sync') {
        return (
          <Button
            variant="secondary"
            size="sm"
            onClick={(e) => { stop(e); fa.apply(useStore.setState, useStore.getState); }}
          >
            {fa.label}
          </Button>
        );
      }

      if (fa.kind === 'value-transfer-picker') {
        return (
          <div className="flex gap-1">
            <Button
              variant="secondary"
              size="sm"
              onClick={(e) => { stop(e); fa.applyLeft(useStore.setState, useStore.getState); }}
            >
              {fa.leftLabel}
            </Button>
            <Button
              variant="secondary"
              size="sm"
              onClick={(e) => { stop(e); fa.applyRight(useStore.setState, useStore.getState); }}
            >
              {fa.rightLabel}
            </Button>
          </div>
        );
      }

      if (fa.kind === 'navigation-only') {
        return (
          <Button
            variant="ghost"
            size="sm"
            onClick={(e) => {
              stop(e);
              // Reuse the existing row click-to-focus path — same behavior as
              // clicking the row itself. Centralize via handleResultClick so
              // there's one focus implementation.
              handleResultClick(result);
            }}
          >
            {fa.label}
          </Button>
        );
      }

      // Exhaustiveness check — TS will error if a new kind is added without a branch.
      const _exhaustive: never = fa;
      return null;
    })()}
    ```

    Key correctness notes for this block:
      - The closures `fa.apply` / `fa.applyLeft` / `fa.applyRight` are called with `useStore.setState` and `useStore.getState` (the actual zustand store API methods) — not snapshot-captured copies. This is the Pitfall 7 mitigation: the closure body inside the rule calls `get()` at invocation time, reading fresh store state.
      - `e.stopPropagation()` MUST fire on every button click — otherwise clicking the fix button would ALSO fire the row's click-to-focus handler, causing a panel-tab re-shuffle on top of the mutation. The `stop` helper makes this uniform.
      - `import { useStore } from "../store/useStore";` is required at the file top. This import is on the COMPONENT side (Plan 09), NOT inside the rule files (Plans 05/06) — the rule files stay pure per D-06.
      - The `_exhaustive: never` line is a TypeScript exhaustiveness check; if Plan 01's FixAction union is ever extended (e.g. a fourth kind), this line forces an explicit branch update at the consumer rather than silently rendering nothing.
