    **FixAction emission (per §3.9 lines 793-795 + 989-993: "error; lossless-sync fix (same shape and UI as z_N — same error, identical treatment)"; canonical example label "Sync n: WallTemperature → 10"):**
      - Capture primitives at rule-run time: `consumerN` (number — the canonical winning value), `sourceId` (string).
      - Build:
        ```ts
        fixAction: {
          kind: 'lossless-sync',
          label: `Sync n to ${consumerN}`,
          apply: (set, get) => {
            // Re-read live state at invocation time to avoid Pitfall 7.
            const live = get();
            // Channel n is canonical (derives from z_N / L); propagate to the source side.
            live.updateNodeParam(sourceId, 'n', consumerN);
          },
        }
        ```
      - **Engineering voice:** the label is `Sync n to 3` — terse, names the parameter and the winning value. Matches the §3.9 canonical example "Sync n: WallTemperature → 10" in spirit. The label intentionally omits the source-instance name because the row description already names both nodes; the button label stays compact ("Sync n to 3" not "Sync wt1.n to 3"). Reject any consumer-voice phrasing.
      - **Channel-wins rationale (documented):** §3.9 line 994 calls this a "lossless" mismatch where "the discretization can be changed without changing the physics meaningfully." Per §3.11 the consumer (Channel/CHF/CAC) owns the geometric discretization via z_N / L; the value source is downstream of that decision. So the apply propagates consumer→source (NOT max-wins, which would be wrong if the user just lowered the channel's n). This differs from zNMatch (Plan 05 Task 1), which uses max-wins because that pair has no canonical side.

    **No store import:** nMatch.ts MUST NOT `import` from `gui/src/store/useStore.ts`. The store handle reaches the closure as a parameter from Plan 09's ValidationPanel click handler (`apply(useStore.setState, useStore.getState)`). Pure-function contract preserved (D-06).
