<objective>
Make Plan 62-06's AlertDialog actually appear when the user right-clicks
a USED resource and selects Delete. The AlertDialog UI is already wired
in `ResourceRow.tsx` (62-06 Task 2) and the existing vitest case at line
313 of `ResourcesTreePanel.test.tsx` passes — but only because the test
fixture seeds `parameters.geometry_ref: uuid`. In the running app, the
live `ParameterForm.tsx` (62-08) writes the geometry UUID under
`parameters.geometry` (the registry param name, not the `_ref`-suffixed
key). The usage-detection `useMemo` in `ResourceRow.tsx` line 77-91 only
checks the `_ref`-suffixed key, so `usages.length` is always 0 in the
live app and `handleDelete` immediately removes the resource without
ever opening the dialog.

This is a key-name mismatch between the data-write path (ParameterForm)
and the data-read path (ResourceRow usage detection). The cleanest fix
is to **detect both key forms** in the usage scan — the registry param
name AND the `_ref`-suffixed legacy key. This keeps the existing
fixtures / tests / codegen working (codeGenerator.ts line 803 already
does this fallback for `power_shape_ref ?? power_shape`) and closes the
gap without forcing a data-migration of every existing `.scp` or test
fixture.

Purpose: Close VERIFICATION.md Critical Gap #2 ("Delete confirmation
AlertDialog missing for used resources"). Root plan 62-06.

Output: Updated usage-detection logic in `ResourceRow.tsx` + new vitest
cases pinning both key forms.
</objective>

<root_cause>
- `gui/src/components/sidebar/ParameterForm.tsx` line 91-101 (PipeGeometry
  case) and line 119-131 (Matrix/power_shape case) both call
  `onParamChange(param.name, uuid)`. `param.name` is the registry name
  — `"geometry"` for Channel/CHF/CAC, `"power_shape"` for HeatDiffusion
  (registry components.json lines 24, 128, 583, 983). So the in-memory
  data path is `node.data.parameters.geometry = "<uuid>"` and
  `node.data.parameters.power_shape = "<uuid>"`.
- `gui/src/components/resources/ResourceRow.tsx` lines 77-91 builds
  `refKey = "geometry_ref" | "power_shape_ref"` then filters
  `nodes.filter(n => params?.[refKey] === resource.uuid)`. The `_ref`
  suffix never matches the live data.
- `gui/src/lib/codeGenerator.ts` line 803 demonstrates the dual-key
  pattern is already an accepted convention in this codebase:
  `data.parameters["power_shape_ref"] ?? data.parameters["power_shape"]`.
  Use the same fallback discipline here.
- The existing test at
  `ResourcesTreePanel.test.tsx:329`
  seeds `parameters: { geometry_ref: uuid }` which masks the bug; the
  test passes but the live app fails.

The fix is purely in the usage-detection scan. The AlertDialog JSX,
state plumbing, and `handleDelete` branching in `ResourceRow.tsx` lines
180-196 are correct and need no change.
</root_cause>
