CONTEXT.md Specifics — the four canonical Power Shape codegen forms:
```
# uniform
power_shape_<name> = ones(nz, nx)

# z_cosine
power_shape_<name> = cosine_power_shape(nz, nx; amplitude=1.0)

# file_loaded
power_shape_<name> = rebin_extensive(readdlm(joinpath(@__DIR__, "shapes/mtr.csv"), ','), (nz, nx))

# unset (sentinel)
power_shape_<name> = ones(nz, nx)  # TODO: fill in your power shape
```

Per RESEARCH §"Open Questions Q2": emit a SEPARATE statement per HeatDiffusion consumer (vs inline at constructor call). The variable name convention: `<resource_name>` for the Geometry case (the resource name IS the variable name — both are valid Julia identifiers by D-19 construction). For PowerShape, the variable name is also the resource's name. The downstream HeatDiffusion constructor references it directly: `@named hd_1 = HeatDiffusion(; nz=10, nx=5, power_shape=<resource_name>, ...)`.

Wait — Q2 reconsidered: "Separate statement per HD consumer" suggests one emit per HeatDiffusion (different `nz`, `nx`). But that produces `power_shape_mtr_for_hd_1 = cosine_power_shape(10, 5)` and `power_shape_mtr_for_hd_2 = cosine_power_shape(20, 8)` — two different variables sharing the same recipe. CONTEXT.md Specifics shows the simpler form: one variable per Resource (`power_shape_mtr`), assuming all consumer HDs share the same `(nz, nx)`. If multiple HDs reuse the same PowerShape with different `(nz, nx)`, the recipe call is parameterized by the consumer's `(nz, nx)` at script-runtime.

Pick the CONTEXT.md form: ONE emit per Resource at the top of the file. Multiple HD consumers each get their own assignment line at the consumer site (resource-name-suffixed by HD instance name when multiple consumers exist with different nz/nx). Concretely:
- Single HD consumer: emit `power_shape_mtr = cosine_power_shape(10, 5; amplitude=1.0)` once in the Resources block; HD constructor uses `power_shape=power_shape_mtr`
- Multiple HD consumers with same (nz, nx): same as above
- Multiple HD consumers with different (nz, nx): emit per-consumer-suffixed variables: `power_shape_mtr_for_hd_1 = ...`, `power_shape_mtr_for_hd_2 = ...`; HD constructor uses `power_shape=power_shape_mtr_for_hd_<i>`

This adds complexity. Decision: **simplification** — always emit per-consumer. Variable name = `power_shape_<resource_name>_for_<hd_instance_name>`. Pros: simple, no need to scan-and-decide. Cons: redundant identical lines when multiple HDs share `(nz, nx)`.

Per UI-SPEC §"Code generation" considerations and RESEARCH Q2 recommendation: **separate statement per HD consumer**. Stick with per-consumer emit.

Per RESEARCH Pitfall 4: a Resource named `pump_1` collides with the default `@named pump_1 = Pump(...)` instance name. Mitigation Option 1 (Conservative, RESEARCH-recommended for Phase 62): emit a `# WARNING: name <X> collides with component <Y>` comment near the resource declaration, like the existing `validateJuliaIdentifier` warning at `codeGenerator.ts:194`. Phase 71 owns the full validation framework.
