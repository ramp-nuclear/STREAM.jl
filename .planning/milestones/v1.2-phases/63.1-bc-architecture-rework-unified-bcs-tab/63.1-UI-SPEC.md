## BCs-Tab Layout (D-09, D-10)

Inside `<TabsContent value="bcs">` of the right-sidebar `ComponentTabs`, two stacked sections:

```
┌─ BCs tab body ───────────────────────────────┐
│  ANCHORS                          (uppercase header, only if hasFlowPort)
│  ┌────────────────────────────────────────┐ │
│  │ AnchorsSection                          │ │
│  │   (empty state OR populated row)        │ │
│  └────────────────────────────────────────┘ │
│  ─── Separator (my-[16px]) ─────────────────  (only if both sections render)
│  EXTERNAL INPUTS                  (uppercase header, only if hasExternalInputs)
│  ┌────────────────────────────────────────┐ │
│  │ BCsTabForm (existing pair-group body)   │ │
│  │   - BCModeDropdown per row              │ │
│  │   - SymmetricSegmentedControl per pair  │ │
│  │   - PromoteButton per row when applicable│ │
│  └────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

**Gating rules:**

- If `hasFlowPort && !hasExternalInputs` (e.g. plain `Pump`, `Resistor`, `Gravity`): only Anchors section, no separator.
- If `!hasFlowPort && hasExternalInputs`: defensively only External Inputs (currently a no-op set — every component with external_inputs also has a FlowPort in v1.2). Hide the section header in that case to avoid two headers when there is only one section.
- If `!hasFlowPort && !hasExternalInputs`: the BCs tab itself should not render (handled by the host `hasBCs` gate in `SidebarPanel`). Defensive empty-state render: a single muted line: `"This component has no boundary conditions."`.

**Section header style** (mirrors the `Properties` header in `SidebarPanel.tsx:323`):

```tsx
<h3 className="text-xs font-semibold uppercase tracking-wide text-muted-foreground leading-[1.3] mb-[8px]">
  Anchors
</h3>
```

Exact strings (load-bearing):

| Surface | Copy |
|---------|------|
| Section header (top) | `Anchors` (rendered uppercase by CSS — write the JSX as `Anchors`, not `ANCHORS`) |
| Section header (bottom) | `External Inputs` |

## Anchors Section — Row Anatomy (D-02, D-04, D-05)

`AnchorEntry = { portField: "port_in.P" | "port_out.P", value: number }`. At most one per node.

### State A — No anchor set (empty state)

```
┌─ Anchors ──────────────────────────────────┐
│  No anchor set                              │  <- muted, text-xs
│  [+ Add anchor]                             │  <- Button variant="outline" size="sm"
└────────────────────────────────────────────┘
```

Empty-state copy: `No anchor set` — muted-foreground, `text-xs`, `mb-[8px]` below header.

Click `+ Add anchor` ⇒ open the row in "edit" mode with default values (`portField: "port_in.P"`, `value: 0`). The button transitions into the populated layout in place; no modal, no popover.

### State B — Anchor set (populated row)

```
┌─ Anchors ──────────────────────────────────┐
│  Port                                        │  <- Label, text-[12px]
│  ┌──────────────────────┐                    │
│  │ port_in.P        ▾   │                    │  <- Select, full-width
│  └──────────────────────┘                    │
│  Pressure (Pa)                               │  <- NumericField label, text-[12px]
│  ┌──────────────────────┐                    │
│  │ 101325              │                    │  <- NumericField input
│  └──────────────────────┘                    │
│                                              │
│  [Clear anchor]                              │  <- Button variant="ghost" size="sm"
└────────────────────────────────────────────┘
```

Field layout: vertical stack, `flex flex-col gap-[8px]`. Container `min-w-0` (matches `BCsTabForm.tsx:179`).

Select options (D-02 enumeration):

| value | display |
|-------|---------|
| `port_in.P` | `port_in.P` |
| `port_out.P` | `port_out.P` |

The display string is the Julia field name verbatim — engineers reading the BCs tab are looking for a one-to-one mapping with the generated `~` equation, so labelling as `Inlet pressure` would obscure rather than help.

Value field:

- `NumericField` with `unit: "Pa"`. Label `Pressure`. Default `0` (the value is dirty until the user edits — accept 0 as a legal Real but the validator at `validation.ts` will flag "No pressure boundary condition" only when `Object.keys(anchors).length === 0`).
- Numeric validation via existing `validateReal` (RESEARCH §"Security Domain"). Invalid input renders the standard `aria-invalid` red border already in `Input` (shadcn default).

Clear button:

- Label: `Clear anchor`
- Variant: `ghost` size: `sm`
- Click ⇒ `clearAnchor(nodeId)`. No confirmation prompt — single keystroke + undo restores it (project-wide undo discipline covers this, RESEARCH Pitfall 4). Confirmation would impose modal friction on a non-destructive operation that the user can immediately undo.

## Promote-to-Shared-Source Button (D-07, D-08)

### Trigger placement

Inline at the end of the Mode dropdown row (same flex row, `gap-[8px]` from `Select`). Right-aligned, does NOT push the dropdown narrower — uses `flex-shrink-0`.

### Visibility rules

Render only when ALL of these hold:

1. `externalInput.source_component` is defined in the registry (i.e. the input has an associated value-source component — `T_wall_*` for Channel, `q_*` for ChannelHeatFlux).
2. `entry?.mode !== "source"` — the input is not already bound to a shared source. Once promoted, the dropdown shows `Source` and the canvas node carries the value; the button disappears.

When hidden, no placeholder — the dropdown simply occupies the full row.

### Visual

| Property | Value |
|----------|-------|
| Variant | `ghost` (shadcn) |
| Size | `icon` (Plan 63.1-13 amend) |
| Icon + label | lucide `MoveUpRight` glyph; accessible name via `aria-label="Promote to shared source"` + shadcn Tooltip carrying the same string on hover. **Revised by Plan 63.1-13 (GAP-COSMETIC-PROMOTE)** per user UAT feedback that the original `↗ Promote to shared source` ghost-text variant was visually too heavy. |
| Hover | `--accent` bg (ghost default) |
| Focus | 3px focus-visible ring (shadcn default) |
| Disabled | When `entry?.mode === "source"` the button does not render (rather than rendering disabled — disabled-state on a hidden affordance is dead UI) |

### Click behavior (visual contract — the data path is in RESEARCH §"Promote to shared source")

1. Optimistic: button click triggers `promoteToSharedSource(nodeId, externalInputName)` synchronously.
2. The store action spawns the corresponding `WallTemperature` / `HeatFluxSource` node at `(consumer.x - 160, consumer.y - 40)` (RESEARCH A6).
3. The dropdown immediately re-renders showing `Source` (the per-mode editor body switches to `SourceModeEditor`).
4. The canvas re-renders with the new node and the dashed BC edge (existing `BCEdge.tsx` visual idiom, unchanged).
5. The button itself disappears (visibility rule 2).

**No spawn animation, no toast.** The simultaneous changes (dropdown shifts to Source, button vanishes, node appears on canvas) are sufficient feedback; an extra toast would be redundant chrome. If user testing flags discoverability of the spawned node, Phase 71/72 may add a brief pulse on the new node — out of scope.

### Empty state for paired-but-asymmetric rows

If the user has the Symmetric toggle ON and clicks Promote on the primary row, the symmetric mirror in `setBCMode` propagates the source-mode entry to the sibling. The button on the sibling row is therefore hidden (it's already in source mode). No special UI needed.

## Canvas Anchor Indicator (D-13)

**Endorsed visual:** small filled circle near the anchored FlowPort handle (RESEARCH §"Anchor indicator (D-13) — recommended treatment").

**Rejected alternatives (with reasons):**

| Alternative | Why rejected |
|-------------|-------------|
| Anchor icon (`Anchor` from lucide) | Adds a 4th glyph language to canvas nodes (after FlowPort circles, ThermalPort diamonds, BC dashed squares). Too much vocabulary; a small dot reads as "marked" without adding semantic noise. |
| Badge on the node body ("⚓ ANCHOR" label) | Steals visual weight from instance name + parameter line. The anchor is a port-level fact; placing it on the node body decouples it from the port that is actually anchored. Loses information. |
| Subtle ring around the handle | Already-used vocabulary for `selected` (ring-2 ring-[var(--ring)]) and `hasAnyError` (red ring). A third ring color creates collision and forces the user to learn ring-color semantics. |

### Specification

| Property | Value |
|----------|-------|
| Shape | Filled circle (`rounded-full`) |
| Size | `6 × 6 px` (`w-1.5 h-1.5`) — small enough to read as a marker, large enough to be unambiguous at default ReactFlow zoom |
| Color | `--foreground` (high contrast on `--card`); inherits theme so it adapts to dark mode automatically |
| Border | None |
| Position | Absolutely positioned next to the anchored FlowPort handle. For a left-side `port_in` handle, offset = `(x: -6px, y: -6px)` from handle center (i.e. just outside the handle, top-left). For a right-side `port_out` handle, offset = `(x: +6px, y: -6px)` (just outside, top-right). The 6px offset puts the marker tangent to the 12px FlowPort handle. |
| Z-index | Above the handle (ReactFlow z layering: marker renders after Handle in JSX — natural stacking) |
| `aria-label` | `"Pressure anchor"` (D-13 — accessible name for screen readers + tests) |
| `data-testid` | `"anchor-indicator"` (test hook) |

### Render gate

```tsx
const hasAnchor = useStore(useCallback(
  (s) => s.anchors[id]?.portField === portFieldKey,
  [id, portFieldKey],
));
```

Render the dot inside the `flowPorts.map(...)` block, as a sibling of `<Handle>`. The selector returns a primitive boolean (RESEARCH Pitfall 1).

### Interaction with existing handle visuals

- Handle dimming for dual-layer nodes (`dimFlowHandles`): the indicator dims with the handle. Apply `opacity: 0.2` when `dimFlowHandles` is true.
- Selected ring: the indicator sits outside the selection ring (`ring-2 ring-[var(--ring)]`); no clipping.
- Error ring (`hasAnyError`): the indicator remains visible — it's a state marker, orthogonal to the error state. (A node can be both anchored and in n-mismatch — the user needs both signals.)

## Validation Surface (selector-derived; D-15..D-19, D-23)

This phase replaces the stored `errorTagsByNodeId` with a memoized `selectNodeErrors(state, nodeId): string[]` selector. The visual contract:

| Tag | Trigger | Canvas surface | Sidebar surface |
|-----|---------|----------------|------------------|
| `bc-n-mismatch` | A source-mode `bcMode` entry connects two nodes whose `n` parameters differ | Red ring on BOTH the consumer and source nodes (existing red-ring chrome at `StreamNode.tsx:149-155`) | None in 63.1 — Phase 71 adds the validation panel entry. The sidebar dropdown remains visually neutral; user reads the source of truth from the canvas. |
| (future) `missing-anchor` | Phase 71 only — global "exactly one anchor per loop" check | Not surfaced in 63.1 | Not surfaced in 63.1 |

**Auto-clearing (D-23):** because the tag is computed on demand by the selector, the red ring disappears on the next render after the underlying mismatch is fixed (e.g., user updates `n` on the source). No explicit cleanup code paths exist.

**The "missing anchor" surface is intentionally NOT added to 63.1.** D-01 + D-19 are explicit: 63.1 sets the foundation only; the global anchor count rule is Phase 71. Adding it now would force a parallel rendering path before the validation framework lands.

- Tab order through the BCs tab (top → bottom): Anchors port `Select` → Anchors value `Input` → Anchors `Clear` button → External Inputs symmetric segmented (if paired) → first FieldRow's `BCModeDropdown` → first FieldRow's per-mode editor → `↗ Promote` button (if visible) → next FieldRow → ...

- `↗ Promote` button: focusable, `Enter`/`Space` triggers the same action as click.

## Properties-Side Mode Dropdown for Value-Source Params (Plan 63.1-14, GAP-RC-4)

> **Deviation from Plan 11 "scalar-only" claim.** Plan 11 intentionally delivered a scalar-only `TypeUnionField` for `WT.T_wall` and `HFS.q` (recorded as "partial step — mode-aware editor deferred" in Plan 11 SUMMARY Decision #3). Plan 14 closes the remaining gap.

### Surface

The Properties tab on a selected `WallTemperature` or `HeatFluxSource` node now shows a 3-option Mode dropdown above the value editor body — mirroring (a strict subset of) the 5-option consumer-side BCs tab Mode dropdown.

### Options (verbatim, in this order)

| value (store) | display (dropdown) |
|--------------|--------------------|
| `value` | `Value` |
| `profile` | `Profile` |
| `function` | `Function` |

`Mark` and `Source` are intentionally absent — those arms are consumer-side concepts (Mark = manual wire in .jl; Source = bound to another source-block). A source-block cannot bind to another source; "mark" has no meaning on a producer.

### Layout

```
PARAMETERS section
──────────────────
n
┌─ T_wall ─────────────────────────────────┐
│  (label row)                              │
│  ┌──────────────────────┐                 │
│  │ Value           ▾   │                 │  <- shadcn Select, full-width
│  └──────────────────────┘                 │
│  (per-mode editor body)                   │
│    Value:    NumericField with unit badge  │
│    Profile:  ProfileModeEditor (reused)    │
│    Function: FunctionModeEditor (reused)   │
└───────────────────────────────────────────┘
```

### Storage shape

`nodeData.parameters["T_wall"]` / `nodeData.parameters["q"]` stores a `SourceValueEntry` discriminated union (declared in `gui/src/lib/sourceValueEntry.ts`):

| Mode | Stored shape |
|------|-------------|
| Value | `{ mode: "value", value: number }` |
| Profile cosine | `{ mode: "profile", preset: "cosine", amplitude: number, peakingFactor: number }` |
| Profile file | `{ mode: "profile", preset: "file", path: string }` |
| Function | `{ mode: "function", signature: "fn(t)" | "fn(t, i)", functionName: string }` |

Pre-Plan-14 `.streamgui` files with bare `number` values break — no migration code per `feedback_no_back_compat_during_heavy_dev`.

### Canvas label (StreamNode.sourceLabelLine)

| Entry shape | Label rendered |
|-------------|---------------|
| `{ mode: "value", value: N }` | `T_wall = N K` (same as previous bare-number path) |
| `{ mode: "profile", preset: "cosine", ... }` | `T_wall = profile (cosine)` |
| `{ mode: "profile", preset: "file", ... }` | `T_wall = profile (file)` |
| `{ mode: "function", ... }` | `T_wall = fn(t)` |
| `undefined` / absent | `T_wall = (unset)` in destructive-red (unchanged) |

### Promote-to-shared-source seed

`promoteToSharedSource` writes `{ mode: "value", value: 300.0 }` (WT) and `{ mode: "value", value: 0.0 }` (HFS) so the spawned source renders a muted-gray `T_wall = 300 K` label from first creation — no destructive-red `(unset)` flash.

### Copywriting additions

| Element | Copy |
|---------|------|
| Mode dropdown options (Properties tab) | `Value`, `Profile`, `Function` (in that order; no Mark or Source) |

### Gating rule

Only Sources-category components expose the Mode dropdown. `Channel.h_left` / `Channel.h_right` (Hydraulic category, `type_union` params) continue to show scalar-only input with "edit in generated Julia" hint.
