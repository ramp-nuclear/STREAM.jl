The addEdge CR-01 sibling-derivation (useStore.ts:1150-1170, paraphrased):
- When connection.targetHandle is set:
  - key = bcModeKey(connection.target, connection.targetHandle)
  - baseField = stripSideSuffix(connection.targetHandle)  -- e.g. "T_wall_left" → "T_wall"
  - symmetric = state.bcSymmetric[`${connection.target}::${baseField}`] ?? true
  - if symmetric: siblingName = siblingExternalInputName(connection.targetHandle) -- "T_wall_left" → "T_wall_right"
  - writes both bcMode[key] AND bcMode[siblingKey] with the same source entry

**Key decision for this plan:** the targetHandle name passed to addEdge MUST be a valid external_input name (T_wall_left / T_wall_right / q_left / q_right) for the sibling derivation to work. If we use `T_wall_target` as the handle name, `siblingExternalInputName("T_wall_target")` returns null (no `_left` / `_right` suffix), and only one bcMode entry would get written.

**Resolution (per planning directives — symmetric default flow):** name the target handle as the **primary side** (the `_left` side, since stripSideSuffix recognises both _left and _right and pairs them). Concretely:
- Channel.ports[] adds `{ name: "T_wall_left", type: "BCPort", array_size: "n", side: "left" }`
- ChannelHeatFlux.ports[] adds `{ name: "q_left", type: "BCPort", array_size: "n", side: "left" }`

The handle id (`T_wall_left`) IS the externalInputName. addEdge picks it up unchanged, sibling derivation flows naturally, both sides materialize when bcSymmetric is ON.

When the user toggles Asymmetric and wants per-side BCs, they use the BCs-tab dropdown to set each side independently — the canvas drag is the symmetric-default convenience entry. This matches D-CD-05 (symmetric by default) and avoids cluttering the canvas with two redundant handles per pair. If the user wants the right-side variant explicitly, they can still set it from the BCs tab.

NOTE: this naming creates a subtle invariant — the BCPort handle on Channel with `name: "T_wall_left"` is a **target** (consumer side), while the BCPort handle on WallTemperature with `name: "T_wall_out"` is a **source** (producer side). Both are tagged `type: "BCPort"` in the registry. StreamNode's bcPorts.map must therefore decide source-vs-target at RENDER time, not at registry time. Heuristic: if the handle's component category is "Sources" (WT, HFS), render type="source"; otherwise render type="target". Alternative heuristic: look at port.side — "right" on Sources, "left" on consumers. Either works; the category check is cleaner because category is already on the registry entry.

Existing isAllowedBCConnection (lib/bcMode.ts:94-110): the connection-validation predicate uses sourceComponentId / targetComponentId — it does NOT inspect handle names. The current allow-list (WallTemperature→Channel, HeatFluxSource→ChannelHeatFlux) is correct and needs no edit.

CanvasPanel.isValidConnection uses isAllowedBCConnection plus a check that the source handle's port type is BCPort (see lib/bcMode.ts file header note "consumed by CanvasPanel.isValidConnection"). Once the target Channel exposes a BCPort target handle, ReactFlow can attempt the drop, isValidConnection accepts it (already does), and addEdge fires.

Plan 10's `_reconcileEdgesForBCMode` helper (useStore.ts:568+) currently keys edges by `e.targetHandle === externalInputName`. The new T_wall_left target handle on Channel is itself the externalInputName, so the helper continues to work without edit.

UI-SPEC §"BCPort handle" (Phase 63-D, inherited): hollow 10×10 square with muted-foreground border on consumer; SAME visual on source (transparent, muted border) — distinguished only by position (left vs right). Phase 72 owns the global "professional" restyle; do NOT introduce a new BCPort target style here.

**Anchor for bcPorts.map source vs target decision (pick exactly one and lock it):**

Recommended: look up the component category for the node being rendered. WT and HFS have `category === "Sources"` (registry confirmed); Channel and CHF have `category === "Hydraulic"`. So inside StreamNode (the rendering component already calls `getComponent(nodeData.componentId)` and stores it as `component`), branch on `component.category === "Sources"` to pick source vs target. This keeps the registry shape minimal (BCPort doesn't need a new `direction` field).
