## Summary

Phase 12.1 is a targeted refactoring phase with a single technical root cause: the existing channel constructors (`Channel`, `ChannelHeatFlux`, `ChannelAndContacts`) hardcode `π*Dh` or `π*Dh/2` as the heated perimeter, which is the circular-pipe formula. For the MTR rectangular channel (`y=0.07 m` per face), the correct heated perimeter per face is `y` (not `π*Dh/2 ≈ 0.01571 m`), a 4.46x mismatch. This error made the Phase 12 VAL-01/02/03 quantitative comparisons against Python STREAM infeasible, so they were replaced by physics-only assertions.

The fix is to introduce a `PipeGeometry` struct that carries `L`, `Dh`, `A`, and `heated_parts::NTuple{2,Float64}`. The three channel constructors accept a `geometry::PipeGeometry` argument and extract scalars from it. Circular geometry is created via `PipeGeometry(; L, D)` (kwargs `D` present), rectangular via `PipeGeometry(; L, Dh, A, y)` (kwarg `y` present). After the Julia refactor, `generate_mtr_reference.py` must be updated to use rectangular MTR geometry in Python STREAM, and then executed to produce new reference constants. Those constants are hardcoded into VAL-01/02/03 with 1% tolerance assertions.

All decisions are locked. This is a pure refactoring + reference-regeneration phase — no new physics, no new MTK patterns, no new numerical methods. The main execution risk is Julia keyword-constructor disambiguation (two outer constructors that differ by kwarg name, not kwarg count) and the mandatory manual checkpoint between the refactor commit and the reference-value commit.

**Primary recommendation:** Two-wave plan: Wave 1 = struct definition + all three channel constructor refactors + all test call-site updates (THERM-01, THERM-03, CHAN-03, HDIFF tests, VAL scaffolding). Wave 2 = run Python script, hardcode constants, add 1% assertions, update STATE.md.

### Pattern 1: Immutable Struct with Keyword Outer Constructors

**What:** Define the inner struct with positional args, then provide keyword-argument outer constructors for the two geometry types. Julia dispatches on which kwargs are provided.

**When to use:** When you want named, self-documenting construction of value types without OOP patterns.

**Implementation:**
```julia
# Inner struct (positional — canonical form)
struct PipeGeometry
    L            ::Float64
    Dh           ::Float64
    A            ::Float64
    heated_parts ::NTuple{2,Float64}
end

# Outer constructor 1: circular pipe (kwarg D distinguishes from rectangular)
function PipeGeometry(; L, D, A = π * D^2 / 4)
    PipeGeometry(L, D, A, (π * D / 2, π * D / 2))
end

# Outer constructor 2: rectangular MTR channel (kwarg y distinguishes from circular)
function PipeGeometry(; L, Dh, A, y)
    PipeGeometry(L, Dh, A, (y, y))
end
```

**Disambiguation:** Circular has kwarg `D`; rectangular has kwarg `y`. Julia will select the correct method because the kwarg sets are disjoint. No ambiguity. If for any reason Julia complains, fall back to named module functions `circular_pipe(...)` / `rectangular_channel(...)` — but this should not be needed.

**Confidence:** HIGH — standard Julia pattern; NTuple{2,Float64} is unambiguous.

### Pattern 2: Extracting Geometry in Constructors (not in helper)

**What:** Channel constructors extract `geometry.L`, `geometry.Dh`, `geometry.A` as local scalars before building equations. `_channel_base_eqs` continues to receive plain Float64 scalars.

**Why:** `_channel_base_eqs` is a low-level helper with a fixed scalar interface. Changing it would break the contract unnecessarily. The extraction belongs at the constructor boundary.

```julia
function ChannelAndContacts(; name, n::Int, geometry::PipeGeometry, g = 0.0)
    Dh  = geometry.Dh
    A   = geometry.A
    L   = geometry.L
    dz  = L / n
    Dt  = Differential(t)
    # ... rest of constructor unchanged except perimeter references
end
```

### Pattern 3: Per-Face vs. Total Perimeter

**What:** `ChannelAndContacts` uses `geometry.heated_parts[1]` (left face) and `geometry.heated_parts[2]` (right face) independently. `Channel` and `ChannelHeatFlux` use `sum(geometry.heated_parts)` for the total perimeter.

**Invariant check for THERM-03:** The two-sided CAC vs. CHF equivalence test requires:
```
geometry_cac.heated_parts[1] == sum(geometry_chf.heated_parts)
```
With circular geometry: `heated_parts[1] = π*D_cac/2`. If `D_cac = 2*D_chf`:
```
π*(2*D_chf)/2 = π*D_chf = π*D_chf/2 + π*D_chf/2 = sum(chf heated_parts)  ✓
```
Existing test parameters (`D_chf=0.01`, `D_cac=0.02`) satisfy this. No change needed to the test logic — only the constructor calls change.

### Anti-Patterns to Avoid

- **Passing `geometry` to `_channel_base_eqs`:** Do not. Extract scalars at the constructor level, pass scalars to the helper.
- **Using `heated_parts[1]` in Channel/ChannelHeatFlux:** They have a single coupled surface; use `sum(geometry.heated_parts)`.
- **Using `sum(heated_parts)` in ChannelAndContacts energy balance:** CAC has two independent faces; per-face indexing is required.
- **Modifying MTK parameter blocks to store PipeGeometry:** The struct is a plain Julia value, not an MTK parameter. Extract `Dh`, `A`, `L` and store those as MTK parameters as before.

## Common Pitfalls

### Pitfall 1: `_channel_base_eqs` Does NOT Accept Geometry

**What goes wrong:** Refactoring `_channel_base_eqs` to accept `PipeGeometry` instead of scalars — breaks all callers, adds unnecessary complexity.
**Why it happens:** Over-refactoring instinct.
**How to avoid:** `_channel_base_eqs` signature is frozen. Only the three channel constructors change. The helper receives `Dh, A, L, g_acc, dz` as scalars extracted by the constructor from geometry.
**Warning signs:** If the plan includes modifying `_channel_base_eqs` arguments, that is out of scope.

### Pitfall 2: `sum(heated_parts)` vs. `heated_parts[1]` confusion

**What goes wrong:** Using per-face `heated_parts[1]` in `Channel` or `ChannelHeatFlux` (single-surface components), or using `sum` in `ChannelAndContacts` (two-face component).
**Why it happens:** Copy-paste between the three constructors without checking semantics.
**How to avoid:** Rule: `ChannelAndContacts` only: per-face indexing. All others: `sum`.
**Warning signs:** THERM-03 fails with T_out mismatch; energy balance is off by 2x.

### Pitfall 3: Keyword Constructor Disambiguation Failure

**What goes wrong:** Julia cannot distinguish `PipeGeometry(; L, D, A)` from `PipeGeometry(; L, Dh, A, y)` if someone uses `Dh` where `D` is expected (or vice versa).
**Why it happens:** Naming inconsistency in call sites.
**How to avoid:** Circular: always pass `D=...` (not `Dh=...`). Rectangular: always pass `Dh=...` and `y=...`. Document this clearly in struct docstring.
**Warning signs:** `MethodError: no method matching PipeGeometry(...)` at a call site.

### Pitfall 4: Python Reference Script Must Be Run AFTER Julia Refactor

**What goes wrong:** Running `generate_mtr_reference.py` before the Julia refactor, then using those constants — they will not match the updated Julia geometry.
**Why it happens:** Eager testing before the correct Julia geometry is committed.
**How to avoid:** The plan must have an explicit wave break: Wave 1 commits the Julia refactor and `generate_mtr_reference.py` update. Wave 2 runs the Python script, captures output, hardcodes constants into runtests.jl.
**Warning signs:** Constants are from the old circular geometry → 1% tests fail even though Julia math is correct.

### Pitfall 5: THERM-03 CAC Adiabatic Test (CHAN-03) Invariant

**What goes wrong:** CHAN-03 uses `D_cac = 0.02` to make one-sided CAC left face match full CHF perimeter. After PipeGeometry refactor, the geometry must continue to satisfy `heated_parts[1]_cac == sum(heated_parts)_chf`.
**Why it happens:** Mechanical call-site update without verifying the invariant.
**How to avoid:** Use circular `PipeGeometry(; L=L_ch, D=D_cac, A=A_ch)` for CHAN-03's CAC. `D_cac=0.02 = 2*D_chf=2*0.01`. Then `heated_parts[1] = π*0.02/2 = π*0.01 = sum(π*0.01/2, π*0.01/2)`. ✓

### Pitfall 6: VAL Test MTK Parameter Blocks Still Carry Old L/D/A

**What goes wrong:** After refactoring the constructors, the MTK `@parameters` block inside Channel/ChannelAndContacts/ChannelHeatFlux still explicitly lists `L`, `D_h`, `A` parameters. These are still correct — they should remain (they enable `remake()` if needed). What changes is how they are assigned: from constructor kwargs directly to extracted from `geometry`.
**Why it happens:** Confusing the struct fields with the MTK parameter block.
**How to avoid:** Keep the `@parameters begin L=L; D_h=Dh; A=A; ... end` block exactly as is — just source `L`, `Dh`, `A` from `geometry.L`, `geometry.Dh`, `geometry.A` at the top of each constructor.

### Pitfall 7: STATE.md Stale Entries

**What goes wrong:** After implementation, STATE.md Key Decisions still reference `π*Dh/2` in three entries, causing future confusion.
**Why it happens:** Forgetting non-code artifacts.
**How to avoid:** The final task of Wave 2 must update STATE.md:
  1. `"q_wall[i] ~ ...each side uses pi*Dh/2"` → update to `geometry.heated_parts[i]`
  2. `"ChannelAndContacts requires explicit thermal.Q_flow equations: h_tc*(pi*Dh/2)*dz*deltaT"` → update formula
  3. `"Python STREAM refs incompatible with Julia MTR geometry"` → REMOVE (problem is fixed)

```julia
struct PipeGeometry
    L            ::Float64                    # pipe/channel length [m]
    Dh           ::Float64                    # hydraulic diameter [m] — Re, Nu, h_tc, dP
    A            ::Float64                    # flow cross-section area [m²]
    heated_parts ::NTuple{2,Float64}          # heated perimeter per face [m]: (left, right)
end

# Circular pipe — preserves existing circular behavior exactly
function PipeGeometry(; L, D, A = π * D^2 / 4)
    PipeGeometry(L, D, A, (π * D / 2, π * D / 2))
end

# Rectangular MTR channel — the geometry fix
function PipeGeometry(; L, Dh, A, y)
    PipeGeometry(L, Dh, A, (y, y))
end
```

### Updated ChannelAndContacts Energy Balance

```julia
# Source: Locked design from 12.1-CONTEXT.md
# Per-cell energy balance: two-sided heating using per-face heated_parts
for i in 1:n
    T_up = (i == 1) ? T_inlet : T[i-1]
    push!(eqs,
        Dt(T[i]) ~ (port_in.mdot * cp_water(T[i]) * (T_up - T[i])
                   + h_tc[i] * geometry.heated_parts[1] * dz * (thermal_left[i].T  - T[i])
                   + h_tc[i] * geometry.heated_parts[2] * dz * (thermal_right[i].T - T[i]))
                  / (rho_water(T[i]) * cp_water(T[i]) * A * dz)
    )
    push!(eqs, thermal_left[i].Q_flow  ~ h_tc[i] * geometry.heated_parts[1] * dz * (thermal_left[i].T  - T[i]))
    push!(eqs, thermal_right[i].Q_flow ~ h_tc[i] * geometry.heated_parts[2] * dz * (thermal_right[i].T - T[i]))
    push!(eqs, q_wall[i] ~ thermal_left[i].Q_flow + thermal_right[i].Q_flow)
end
```

### Updated ChannelHeatFlux Energy Balance

```julia
# Source: Locked design from 12.1-CONTEXT.md
# Total perimeter = sum(heated_parts); for circular: π*D/2 + π*D/2 = π*D (same as before)
for i in 1:n
    T_up = (i == 1) ? T_inlet : T[i-1]
    push!(eqs,
        Dt(T[i]) ~ (port_in.mdot * cp_water(T[i]) * (T_up - T[i])
                   + h_tc[i] * sum(geometry.heated_parts) * dz * (T_wall_p - T[i]))
                  / (rho_water(T[i]) * cp_water(T[i]) * A * dz)
    )
    push!(eqs, q_wall[i] ~ h_tc[i] * sum(geometry.heated_parts) * dz * (T_wall_p - T[i]))
end
```
