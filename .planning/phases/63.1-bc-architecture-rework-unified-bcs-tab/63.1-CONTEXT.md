# Phase 63.1 — Carry-Over Context

This file captures decisions and open questions agreed during the Phase 63 wrap-up discussion (2026-05-13), before `/gsd:discuss-phase 63.1` runs formally. The discuss-phase workflow should treat the **Locked decisions** as inputs (do not re-litigate them) and use the **Open questions** as its starting question set.

---

## Why this phase exists

Phase 63 shipped the BCs-tab + Sources-component design as scoped, but use-testing surfaced three classes of problems:

1. **Correctness bugs in what shipped.** Canvas-drag of a BC edge half-creates the wiring (CR-01 in `63-REVIEW.md`); `setBCSymmetric` has two transition-edge holes (CR-02, CR-03); n-mismatch red ring doesn't clear after the user fixes the mismatch; click-and-drag on a node doesn't refresh the Properties panel.

2. **Architecture: Sources-as-canvas-nodes is the wrong default.** For the dominant case (one channel, one BC, one value) it's 5 steps to do what is conceptually one thing. The Source node + dashed edge + BCs tab is three places to look for the same datum. User feedback: "feels amateur" — copying Modelica's pattern without thinking about whether a higher-level GUI should expose it that way.

3. **UX: pill mode picker advertises the rarest action.** Mode-change is rare; value-edit is common. Pills give mode the dominant visual weight. The symmetric toggle's "L=R" label is engineer-speak ambiguous about what state the toggle is currently in.

Phase 63 is marked **complete** with these items documented in `.planning/phases/63-bcs-tab-value-source-components-in-gui/63-HUMAN-UAT.md` and `63-REVIEW.md`. Phase 63.1 is the redesign that addresses them all in one coherent pass — fixing CR-01 in isolation and then deleting Sources next phase would be wasted work.

## Locked decisions (do not re-litigate)

These were agreed in the wrap-up discussion. Discuss-phase should treat them as inputs.

### A. BCs tab is the single surface for all binding-related UI

No separate "Sources" workflow. No second panel. Every kind of binding on a component is set in the BCs tab.

### B. Sources component nodes are hidden by default; opt-in via "promote to shared source"

- Default behavior: BCs set inline in the BCs tab. No `WallTemperature` / `HeatFluxSource` node on the canvas, no dashed edge.
- The Sources toolbox category is **removed from the default toolbox**.
- The BCs tab gains an inline "↗ Promote to shared source" action. When invoked, it spawns the corresponding `WT` / `HFS` node, replaces the inline value with a reference, and creates the dashed edge.
- Rationale: shared BCs across components are a real engineering scenario (parallel channels with the same wall-temperature profile, symmetric plates) — when sharing matters, the canvas should show it. When it doesn't, the canvas stays clean.

### C. BCs tab has two sections: "Anchors" and "External Inputs"

- **Anchors** — structural bindings required to make the DAE solvable (pressure anchor for now; possibly gravity reference and transient initial conditions — see Open Questions).
- **External Inputs** — the existing 5-mode picker stuff for the component's `external_inputs` (`T_wall`, `q_flux`, etc.).
- Same tab, clearly-labeled sections. Different *kind* of binding, same conceptual question ("what's bound on this component?").
- Why not unify them under the 5-mode picker: pressure anchor is always a scalar and has a global "exactly one per loop" invariant — pretending it uses the 5-mode picker would be fiction.

### D. BCs tab stays in the right sidebar next to Properties

Moving it elsewhere splits attention for the same component. What needs to change isn't *where* the tab is — it's the visual weight inside the panel (see UX changes below).

### E. UX: mode picker becomes a dropdown; symmetric becomes a labeled segmented control

- 5-pill `BCModePicker` → dropdown (mode is the rare action; the value editor should get full width).
- "L=R" symmetric switch → labeled segmented control: `Symmetric | Asymmetric`. Strip the ambiguity.

### F. Bugs to fix in this phase

All in scope; the redesign and the fixes ship together.

- **CR-01** — canvas-drag of a BC edge sets `edges[]` but does NOT write the `bcMode` entry. Codepath: `gui/src/store/useStore.ts:1047-1062` (`addEdge` BCPort branch). REVIEW.md has drop-in fix code.
- **CR-02** — `setBCSymmetric(true)` "left wins" doesn't handle `leftEntry === undefined && rightEntry !== undefined`. Codepath: `gui/src/store/useStore.ts:~1298`.
- **CR-03** — `setBCSymmetric(true)` mirrors `bcMode` but does NOT sync the BC edges or n-mismatch tags. Same codepath as CR-02.
- **Click-vs-drag selection bug** — clicking a node opens its Properties; click-and-drag does not change which node's Properties show. New bug reported during use-testing.
- **N-mismatch ring lifecycle** — fixing the n-mismatch after edges are connected does not clear the red ring on either endpoint. Likely the same root cause as CR-03 (no resync after relevant state changes).

## Open questions for discuss-phase

These are the things we explicitly deferred to `/gsd:discuss-phase 63.1`. Each one is a real decision the workflow should surface.

### Q1. What else counts as an "Anchor" beyond pressure?

- Pressure anchor — yes, confirmed.
- Gravity reference — maybe? It's structural-ish (pins potential energy datum) but currently handled per-component via `Gravity(H)`. Need to check whether the GUI needs a separate anchor UI for it or whether it's just a property.
- Transient initial conditions — maybe? `solve_transient` needs ICs for state variables; today these come from `steady_state_guess` or user-supplied. Does the BCs tab need an "initial state" section, or is that out of scope for v1.2?
- Anything I'm not thinking of — discuss-phase should do an exhaustive sweep of what the user has to set on a component to make the model run, beyond the constructor kwargs.

### Q2. How does pressure anchor map onto the new BCs-tab data path?

Before locking the schema, need to read:
- `src/components/channels.jl` — where is the pressure anchor variable defined?
- `src/composition/helpers.jl` — how does composition wire pressure anchors today?
- `gui/src/lib/codeGenerator.ts` — what does current code-gen emit for pressure anchor?
- The Phase 71 validation framework intent — how does "exactly one anchor per loop" get encoded?

This is a read-the-code task for discuss-phase / research-phase.

### Q3. Canvas indicator for anchored ports?

Probably yes — discoverability matters. A small icon on the anchored port? A subtle ring on the anchored node? Defer the visual treatment to UI-phase if 63.1 gets one, but the principle decision (is there a canvas indicator or not?) belongs in discuss-phase.

### Q4. Migration path for existing `.streamgui` files

Files saved with the Phase 63 schema (Sources as canvas nodes, BC edges) need to load correctly in the new design. Two reasonable options:
- **Auto-convert on load**: existing Sources stay as canvas nodes (they're now "shared" by definition); inline BCs that were Source-mode against a single component get inlined into the BCs tab.
- **Schema migration on save**: load as-is, save in new schema, one-time upgrade per file.

Pick one in discuss-phase.

### Q5. "Promote to shared source" — what triggers it?

- A button in the BCs tab next to the mode dropdown?
- A right-click menu on the bound BC?
- Auto-promotion when the user tries to bind a second component to the same value?

This is a UI-flow question for discuss-phase / ui-phase.

### Q6. n-mismatch ring lifecycle — who owns the cleanup?

When fixing the ring-doesn't-clear bug: should the validator run on every store mutation that touches `n`-relevant fields, or should it be event-driven (on edge add/remove and on parameter edit)? Performance vs. correctness tradeoff — discuss-phase should pick the model.
