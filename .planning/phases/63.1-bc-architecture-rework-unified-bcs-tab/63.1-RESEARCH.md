# Phase 63.1: BC architecture rework — unified BCs tab — Research

**Researched:** 2026-05-13
**Domain:** Tauri/React/Zustand GUI state-shape change + memoized selector validation pivot + UX rework
**Confidence:** HIGH (codebase facts directly read; no external library reach required)

## Summary

This phase reworks the BC architecture that shipped in Phase 63. It bundles three structural pivots with five concrete bug fixes:

1. **State-shape pivot for anchors** — replace the legacy `bcs: BCEntry[]` slice (a global list of pressure-anchor entries) with `anchors: Record<nodeId, AnchorEntry>` (per-component, at most one entry per node). Delete `BCPanel.tsx` and remove the bottom-panel "BCs" tab. Anchors render in the right-sidebar BCs tab inside a new "Anchors" section above the existing "External Inputs" section.
2. **Validator-architecture pivot** — delete the stored `errorTagsByNodeId` slice and the inline `_checkBCNMismatch` mutator. Replace with a memoized `selectNodeErrors(nodeId)` selector that reads authoritative state (`nodes`, `edges`, `bcMode`, `bcSymmetric`, `anchors`) and recomputes ring/error state on demand. This eliminates the entire stale-derived-state bug class (which produced CR-03's n-mismatch-ring residue, the click-vs-drag stale-Properties bug, and other variants).
3. **UX rework** — replace the 5-pill `BCModePicker` with a dropdown (`Select` primitive); replace the "L=R" custom switch with a `Symmetric | Asymmetric` segmented control (existing `SegmentedButtonGroup` primitive); hide WT/HFS from the default toolbox; surface a per-row "↗ Promote to shared source" button next to the mode dropdown.

Plus bug fixes: CR-01 (canvas-drag-no-bcMode write), CR-02/CR-03 (symmetric-toggle reconciliation holes), click-vs-drag selection not refreshing Properties (root cause: `selectedNodeId` slice never reflects ReactFlow's `select` change events), and n-mismatch ring stale lifecycle (subsumed by the selector pivot).

**Primary recommendation:** Sequence the work in three serial waves — (Wave 0) validation tests for the new selector before writing it; (Wave 1) selector-derived validator infrastructure + delete `errorTagsByNodeId` (foundational, biggest blast radius); (Wave 2) anchors slice + codegen + delete `BCPanel`/`bottom BCs tab` (state-shape change, codegen change, persistence change); (Wave 3) UI surface rework (dropdown, segmented control, Promote button, canvas anchor indicator, toolbox hide). Bug fixes ride inside the relevant wave (CR-01/02/03 land in Wave 1 or 2; click-vs-drag is a small standalone fix anywhere). This ordering minimizes cross-task conflicts and respects the "selector pivot subsumes some bug fixes" relationship.

### Locked Decisions

**Anchors section scope**
- **D-01:** Pressure anchor is the ONLY kind of anchor exposed in the BCs-tab Anchors section in this phase. Gravity reference stays a per-component property via `Gravity(H)` and `check_gravity_mismatch` (unchanged). Transient initial conditions are deferred to a later phase — `solve_transient` continues to source ICs from `steady_state_guess` or user-supplied as today.

**Anchor data path**
- **D-02:** Introduce a new store slice `anchors: Record<nodeId, AnchorEntry>` where `AnchorEntry = { portField: "port_in.P" | "port_out.P", value: number }`. The Record shape enforces at most one anchor entry per component (overwriting on second set is the correct semantics). Multiple components MAY have anchor entries; the Phase 71 validation framework enforces the global "exactly one anchor per loop" invariant — 63.1 does not implement that global validator.
- **D-03:** Delete the legacy `bcs: BCEntry[]` slice and the freestanding `BCPanel.tsx`. All anchor rendering moves into the per-component BCs tab Anchors section. Single source of truth, single rendering site.
- **D-04:** The Anchors section only renders for components that have a `FlowPort` (Pump, Channel, ChannelHeatFlux, ChannelAndContacts, Resistor, Inertia, HeatExchanger, …). Components without a flow port (e.g. `WallTemperature`, `HeatFluxSource`) never display the Anchors section.
- **D-05:** Codegen iterates `Object.entries(anchors)` and emits `${instanceName}.${portField} ~ ${value}` lines. This replaces the current `bcs[]` codegen path.

**Sources-as-canvas-nodes (hidden by default)**
- **D-06:** Sources toolbox category removed from the default toolbox. Inline BCs in the BCs tab are the default.
- **D-07:** "↗ Promote to shared source" trigger is a **button next to the mode dropdown** in the External Inputs row of the BCs tab. (No right-click menu; no auto-promote on second-bind detection.) Discoverability over implicit magic.
- **D-08:** When invoked, "Promote to shared source" spawns the corresponding `WallTemperature` / `HeatFluxSource` node on the canvas at a reasonable default position, replaces the inline value on the originating component with a reference to that node, and creates the dashed BC edge.

**BCs tab layout**
- **D-09:** Two clearly-labeled sections inside the right-sidebar BCs tab: **Anchors** (top) and **External Inputs** (below). - **D-12:** Replace the "L=R" symmetric switch with a labeled **segmented control: `Symmetric | Asymmetric`**. Strips the engineer-speak ambiguity about which state the toggle is currently in.

**Canvas indicators**
- **D-13:** The canvas displays a small visual indicator on ports/nodes that carry an anchor entry. **Migration / back-compat**
- **D-14:** **No migration path** for Phase-63-era `.streamgui` files. STREAM.jl and the Composer GUI are in heavy development; old saved files are accepted to break. Do NOT write a schema upgrader, a "load old shape" fallback, or a parallel legacy UI.

**Validator architecture**
- **D-15:** Delete the stored `errorTagsByNodeId` slice. Replace with a **memoized selector** (`selectNodeErrors(nodeId)` or equivalent) that reads current `nodes`, `edges`, `bcMode`, `anchors`, `bcSymmetric` and computes the ring/error state on demand. No stored cleanup step exists because there is no stored state to go stale.
- **D-16:** Rationale: CR-03, the n-mismatch ring-stale bug, and the click-vs-drag stale-Properties bug all share one root cause — stored derived state going stale relative to authoritative state. - **D-17:** Memoize the selector (`reselect`-style or zustand-shallow-equal) so render cost stays trivial. Graph sizes are small (tens of components, not thousands) — recompute on every store mutation is acceptable; memoization is for re-render avoidance, not for correctness.
- **D-18:** All current consumers of `errorTagsByNodeId` (canvas node ring rendering, any badges) must be migrated to read through the selector. No parallel-storage shortcut.
- **D-19:** Phase 71 validation framework is expected to extend this same pattern (each validator = a selector). 63.1 sets the foundation but does NOT implement the full framework.

### Pattern 1: Selector-derived validator (D-15..D-19)

**What:** A pure function `selectNodeErrors(state, nodeId) → string[]` reads authoritative slices and returns the current set of error tags for that node. No stored mirror. Consumers subscribe via `useStore(useCallback(s => selectNodeErrors(s, id).length > 0, [id]))` — returning a **primitive boolean**, matching the proven loop-safe pattern at `StreamNode.tsx:84-90`.

**When to use:** Any derived predicate / ring-state / badge-state computed from authoritative slices. Validators are selectors. Phase 71 will add more selectors on the same pattern.

**Example:**
```ts
// Source: gui/src/lib/selectors/nodeErrors.ts (NEW)
import type { Node, Edge } from "@xyflow/react";
import type { BCModeEntry } from "../bcMode";
import { bcModeKey } from "../bcMode";

export interface NodeErrorsInput {
  nodes: Node[];
  edges: Edge[];
  bcMode: Record<string, BCModeEntry>;
  bcSymmetric: Record<string, boolean>;
  anchors: Record<string, AnchorEntry>;  // future-use; D-15 explicit
}

/** Pure: compute current error tags for one node. */
export function selectNodeErrors(
  state: NodeErrorsInput,
  nodeId: string,
): string[] {
  const tags: string[] = [];

  // bc-n-mismatch: any source-mode bcMode entry pointing at a node with n≠ours
  const node = state.nodes.find((n) => n.id === nodeId);
  if (!node) return tags;
  const myN = (node.data as { parameters?: Record<string, unknown> })
    ?.parameters?.["n"];

  // Consumer side: this node has a source-mode bcMode entry whose source has n≠my n
  for (const [key, entry] of Object.entries(state.bcMode)) {
    if (!key.startsWith(`${nodeId}::`)) continue;
    if (entry.mode !== "source") continue;
    const src = state.nodes.find((n) => n.id === entry.sourceNodeId);
    if (!src) continue;
    const srcN = (src.data as { parameters?: Record<string, unknown> })
      ?.parameters?.["n"];
    if (typeof myN === "number" && typeof srcN === "number" && myN !== srcN) {
      tags.push("bc-n-mismatch");
      break;  // one tag is enough
    }
  }

  // Source side: this node is the source of a source-mode bcMode entry whose consumer n≠my n
  if (!tags.includes("bc-n-mismatch")) {
    for (const [key, entry] of Object.entries(state.bcMode)) {
      if (entry.mode !== "source" || entry.sourceNodeId !== nodeId) continue;
      const consumerId = key.split("::")[0];
      const consumer = state.nodes.find((n) => n.id === consumerId);
      if (!consumer) continue;
      const consN = (consumer.data as { parameters?: Record<string, unknown> })
        ?.parameters?.["n"];
      if (typeof myN === "number" && typeof consN === "number" && myN !== consN) {
        tags.push("bc-n-mismatch");
        break;
      }
    }
  }

  return tags;
}
```

Consumer pattern (loop-safe):
```ts
// Source: gui/src/components/StreamNode.tsx (CHANGED)
const hasBCError = useStore(
  useCallback(
    (s) => selectNodeErrors(s, id).length > 0,
    [id],
  ),
);
```

### Anti-Patterns to Avoid

- **Don't store any derived BC state.** The whole point of D-15 is to eliminate the parallel-storage class. If a planner is tempted to add `anchorsMissing: Set<nodeId>` or `bcErrors: Record<nodeId, string[]>`, that's the same bug being reinvented.
- **Don't write a `.scp` migration shim.** D-14 is explicit. Old saves break.
- **Don't add a third tier of BC state.** Anchors live in `anchors`. External-input bindings live in `bcMode` + `bcSymmetric` (unchanged). No "general BCs" slice.
- **Don't recompute selectors in render bodies.** Always wrap in `useStore(useCallback(s => …, [deps]))` and return primitives (boolean / number / string). Returning fresh arrays/objects on each render is the proven cause of `Maximum update depth exceeded` (see the StreamNode.tsx:83-84 comment block from Phase 63-D).
- **Don't reach into the registry from BCPort connection validation.** `isAllowedBCConnection` (bcMode.ts:94) stays pure — already correct.

## Common Pitfalls

### Pitfall 1: Maximum update depth exceeded from selector returning fresh array

**What goes wrong:** `useStore(s => selectNodeErrors(s, id))` returns a fresh `string[]` on every render. Zustand's default equality is `Object.is` — fresh array fails it → re-render → fresh array → infinite loop.

**Why it happens:** This is the exact bug Phase 63-D hit and documented in `StreamNode.tsx:80-83`: "Select a primitive (boolean) — not a fresh array — to keep zustand's shallow equality stable and avoid the maximum-update-depth re-render loop."

**How to avoid:** Always return a **primitive** from the selector hook. If you need multiple bits of derived state, use multiple selector hooks. Or use `zustand/shallow` (but project hasn't adopted it; stick with primitives).

**Warning signs:** Test fails with "Maximum update depth exceeded" — or the dev server stalls on a component select.

### Pitfall 2: Selector closure stale-closing over `nodeId`

**What goes wrong:** `useStore(s => selectNodeErrors(s, nodeId))` — without `useCallback`, React re-creates the selector function each render. Each fresh function fails reference equality → forced re-subscribe. Same bug as Pitfall 1 in shape but a different mechanism.

**How to avoid:** `useStore(useCallback(s => selectNodeErrors(s, id).length > 0, [id]))`. The `[id]` dep array stabilizes the closure across renders within the same node.

**Warning signs:** Re-renders increase O(canvas size); profiler shows the component re-rendering every keystroke even when unrelated state changes.

### Pitfall 3: `validateTopology` still requires `bcs.length > 0`

**What goes wrong:** `gui/src/lib/validation.ts:110` reads `if (bcs.length === 0) { systemErrors.push("No pressure boundary condition"); }`. After the slice rename, this check must read `Object.keys(anchors).length === 0`. Forgetting it means the export gate (`validateAndGate` at `useStore.ts:1639`) trivially passes with no anchor — codegen produces an under-constrained model.

**How to avoid:** Signature change is part of the slice change task. `validateTopology(nodes, edges, anchors, getComponentDef)`. All 14 validation.test.ts test calls must update too.

**Warning signs:** Phase smoke fails — export button passes validation but generated `.jl` has no `~ pressure` line.

### Pitfall 4: `_pushSnapshot` undo discipline missing on the new `anchors` slice

**What goes wrong:** `CanvasSnapshot` (`useStore.ts:134-143`) lists every undoable slice. Forgetting to add `anchors: Record<string, AnchorEntry>` means `setAnchor` / `clearAnchor` won't be undoable, breaking the project's undo contract for what is effectively the user's pressure-value input.

**How to avoid:** Update `CanvasSnapshot` + `_pushSnapshot` + `undo` + `redo` paths simultaneously. The Phase 62 Resources slice extension (`useStore.ts:1112` comment) and Phase 63 BC slice extension (`useStore.ts:132-133` comment) are the templates.

**Warning signs:** Manual smoke — set anchor, press Ctrl+Z, anchor doesn't revert.

### Pitfall 5: Removing `errorTagsByNodeId` from `CanvasSnapshot` breaks existing snapshots stack

**What goes wrong:** The undo stack already contains snapshots with `errorTagsByNodeId` populated. After deleting the field from the type, those snapshots have a stale field — but since snapshots are in-memory only (not persisted), and we're not running pre-existing snapshots through the new code, this is fine in practice. **However**, if a developer's dev session has a stuck history at HMR time, the type-check may complain. Solution: rebuild from scratch (no dev preserves undo across HMR by design).

**How to avoid:** Treat the type change as a clean break. No backfill needed because undo state is ephemeral.

### Pitfall 6: ReactFlow `select` NodeChange not synced to `selectedNodeId`

**What goes wrong (the click-vs-drag bug):** `onNodeClick` in `CanvasPanel.tsx:130-138` calls `selectNode(node.id)`. But during a drag-start, ReactFlow emits a `NodeChange.select` event to `onNodesChange`, which `applyNodeChanges` writes to `nodes[].selected` — but no code path updates `selectedNodeId`. So Properties pane keeps showing the previous selection.

**Root cause confirmed:** `useStore.ts:886-903` `onNodesChange` skips contentless events (good) but never inspects `select` changes to update `selectedNodeId`.

**How to avoid:** In `onNodesChange`, after `applyNodeChanges`, find the first `change.type === "select" && change.selected` (most recent select-event from ReactFlow) and dispatch `selectNode(change.id)`. Two-sided: also handle `selected: false` to clear if nothing else is selected.

**Warning signs:** Click a node — Properties shows it. Click-and-drag the same node — Properties keeps showing the previous node.

### Pitfall 7: BCPort handle still rendered on hidden source components

**What goes wrong:** D-06 hides WT/HFS from the toolbox. But existing canvas nodes still render via `StreamNode.tsx`. If a `.scp` had a WT node on the canvas and someone deletes the toolbox category, the node still renders fine. The hiding is **toolbox-only**, not canvas-rendering — important to keep both flows correct.

**How to avoid:** ToolboxPanel.tsx change is purely the visible list. Registry entries for WT/HFS stay (programmatic `addNode("WallTemperature", ...)` from the Promote button must work).

### Pitfall 8: `Object.values(bcMode).some(...)` for DelimitedFiles detection still works

**What goes wrong / what doesn't:** `codeGenerator.ts:718` detects `profile/file` BC modes to gate the `DelimitedFiles` import. After the bcs[] → anchors rename, this branch doesn't change (it reads `bcsState.bcMode`, not `bcs`). No risk; flagging as a "stays correct" reference.

## Open Questions

1. **Should anchors be persisted in `.scp` going forward?**
   - What we know: Legacy `bcs[]` IS persisted (`projectIO.ts:54,89,130,197,205`). Current `bcMode`/`bcSymmetric` are NOT persisted (in-memory only — verified by reading `serializeProject`/`SerializeProjectArgs` at `projectIO.ts:86-98`).
   - What's unclear: D-02 doesn't say. D-14 forbids migration. Strict reading: persist `anchors` (it's a content field, like the legacy `bcs`); leave `bcMode`/`bcSymmetric` non-persisted (matching current behavior).
   - Recommendation: **Persist `anchors`**. The user's pressure-anchor value IS content (not UI state); losing it between save/load sessions would be obvious data loss. This matches the v1.x precedent.

2. **Should `bcMode` / `bcSymmetric` also persist now?**
   - What we know: They currently don't (Phase 63 omission per the grep above).
   - What's unclear: Phase 63 verification mentions this implicitly but never as a "gap". The carry-over context for 63.1 doesn't raise it.
   - Recommendation: Out of 63.1 scope. Flag for future discussion but do NOT bundle into this phase — adds a fourth structural pivot to an already-big phase. Persisting `anchors` only is the conservative move.

3. **`gui/export_examples/*.streamgui` example files (8 files at repo root + 5 referenced in tests):**
   - What we know: They carry the old `bcs[]` schema. The git-untracked ones (`abc.streamgui`, `dwkada.streamgui`, etc.) appear to be user-test scratch files.
   - What's unclear: Do they need updating, or are they accepted to break per D-14?
   - Recommendation: Accept to break (D-14). User can re-save them or delete.

4. **What happens to the `bc-n-mismatch` red ring while a connection is in-flight (mid-drag)?**
   - What we know: Selector recomputes on every state change. During drag, `nodes` and `edges` are stable; only `connection` (from `useConnection()`) changes. So the ring won't flicker.
   - What's unclear: Does Phase 71's expected validator panel need an "in-flight" hook? Not for 63.1.
