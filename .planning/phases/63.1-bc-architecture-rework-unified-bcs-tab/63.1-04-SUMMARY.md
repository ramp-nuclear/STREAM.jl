# Phase 63.1 Plan 04: Codegen + validation contract swap — generateCode and validateTopology now consume the anchors Record (BCEntry retired)

Replace `generateCode`'s `bcs: BCEntry[]` parameter with
`anchorsState: CodegenAnchorsState`, swap `validateTopology`'s 3rd arg
from `BCEntry[]` to `Record<string, AnchorEntry>`, physically remove the
`BCEntry` interface from `codeGenerator.ts`, and migrate every caller
(Toolbar, CodePreview, useStore.validateAndGate, plus three codegen test
files that still passed Array fixtures) to the Record shape. The
end-to-end pipeline `anchors slice → codegen → Julia .jl → validator`
operates without `BCEntry` anywhere in the source tree.

```ts
// REMOVED: export interface BCEntry { ... }

export function generateCode(
  nodes: Node[],
  edges: Edge[],
  anchorsState: CodegenAnchorsState,    // was: bcs: BCEntry[]
  getComponent: (id: string) => ComponentDefinition | undefined,
  resources?: CodegenResources,
  bcsState?: CodegenBCsState,
): string

// New emission loop (replaces `for (const bc of bcs)`)
// Pressure anchors (D-05)
for (const [nodeId, entry] of Object.entries(anchorsState.anchors)) {
  const data = nodeDataMap.get(nodeId);
  if (!data) continue;
  const asm = nodeToAssembly.get(nodeId);
  const prefix = asm ? `${asm.assemblyName}.` : "";
  lines.push(
    `    ${prefix}${data.instanceName}.${entry.portField} ~ ${formatReal(entry.value)},`,
  );
}
```

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] codeGenerator.anchors.test.ts expected `"1.0e5"` / `"2.0e5"` substrings did not match `formatReal`'s actual output**

- **Found during:** Task 1 verify step.
- **Issue:** Plan-01 (Wave-0 RED) wrote the assertions
  `expect(code).toContain("pump1.port_in.P ~ 1.0e5")` and
  `toMatch(/.../pump2\.port_out\.P ~ 2\.0e5/)`. The codegen helper
  `formatReal(n)` calls `String(n)` and appends `".0"` only if the
  result has no `.` / `e` / `E`. `String(1e5) === "100000"`, so
  `formatReal(1e5) === "100000.0"` — never `"1.0e5"`. The Plan-01
  author's substring expectations were wrong (ironically, they would
  have been correct for `1e21` where JS preserves scientific notation).
- **Fix:** Corrected the substrings to `"100000.0"` / `"200000.0"` and
  removed the `@ts-nocheck` + Wave-3 placeholder header. The test's
  intent (per-anchor emission verifies the binding line shape) is
  preserved exactly.
- **Files modified:** `gui/src/lib/__tests__/codeGenerator.anchors.test.ts`
- **Commit:** `bbe11b3`.

**2. [Rule 3 — Blocking] Three additional codegen-test files (`codeGenerator.test.ts`, `codeGenerator.smoke.test.ts`, `codeGenerator.resources.test.ts`) were not in any plan task's `<files>` but had to be migrated**

- **Found during:** Task 1 tsc gate.
- **Issue:** All three files import `BCEntry` from `codeGenerator.ts`
  and pass either `[]` (NO_BCS) or `BCEntry[]` arrays as the third
  positional arg of `generateCode`. Once Task 1 removed `BCEntry` and
  changed the signature, `tsc --noEmit` failed with TS2305 ("BCEntry
  has no exported member") and TS2345 ("Argument of type 'BCEntry[]' is
  not assignable to type 'CodegenAnchorsState'") across these files.
  The plan's must-haves explicitly require `tsc --noEmit` to exit 0 at
  Task 1 done; that gate cannot pass without migrating these callers.
- **Fix:** Bundled the three caller updates into Task 3's commit
  (`d72ecf6`) alongside the planned Toolbar/CodePreview changes. Each
  test gets either a `NO_ANCHORS` constant, a small local `anchors(...)`
  helper, or both. Test semantics are preserved (the BC-fixture inputs
  still produce identical Julia output strings; only the input shape
  changes from Array to Record).
- **Files modified:** `gui/src/lib/codeGenerator.test.ts`,
  `gui/src/lib/__tests__/codeGenerator.smoke.test.ts`,
  `gui/src/lib/__tests__/codeGenerator.resources.test.ts`
- **Commit:** `d72ecf6` (Task 3).

**3. [Plan-internal scoping] `useStore.ts:validateAndGate` was migrated in Task 2's commit rather than Task 3**

- **Found during:** Task 2 implementation.
- **Issue:** The plan's Task 3 step C says "useStore.ts validateAndGate:
  ensure the 3rd argument is `get().anchors` (Record), not
  `get().bcs` (Array)." Mechanically this fits in Task 3. However,
  validateAndGate is the only production caller of `validateTopology`,
  and that contract change is the entirety of Task 2. Splitting the
  validateTopology signature change (Task 2) from its call-site update
  (Task 3) would leave Task 2 in a tsc-broken state (validateAndGate
  passing a `BCEntry[]` to a function that no longer accepts it).
- **Fix:** Moved the `validateAndGate` 3-line edit into Task 2's commit
  (`e930a25`) so the validateTopology contract migration is one atomic
  step. The Toolbar/CodePreview generateCode-caller updates remain in
  Task 3 (they parallel each other and naturally co-locate).
- **Files modified:** `gui/src/store/useStore.ts`
- **Commit:** `e930a25` (Task 2).
