# MTR Channel L/R Convention — Research & Recommendation

**TL;DR:** The MTR L/R parity FAIL is **not a bug in `src/composition/helpers.jl`** as the integration checker first suspected. The helpers are correct and match Python STREAM's physical wiring. The bug is in the **test** at `test/test_validation.jl:371-374` (mtr_symmetric), `:542-545` (mtr_asymmetric), and `:707-708` (mtr_one_sided): the parity scenarios hand-wire connections instead of calling `plate()` / `symmetric_plate()`, and they wire the **wrong channel face** to the fuel.

The fix is a small edit to the test, not a library change.

---

## 1. Both libraries agree on physics

Python's `stream/composition/mtr_geometry.py:38-66` `plate(channel_l, channel_r, fuel)` and Julia's `src/composition/helpers.jl:217-230` `plate(ch_left, ch_right, fuel)` both implement the geometrically correct wiring:

> **Left channel's RIGHT face touches plate's LEFT face. Right channel's LEFT face touches plate's RIGHT face. The opposite faces of each channel are adiabatic.**

This matches the user's stated geometric intuition (2026-05-08).

**Julia helper (correct):**
```julia
# src/composition/helpers.jl:217-230
function plate(ch_left, ch_right, fuel; name::Symbol)
    n = _infer_n(ch_left)
    connections = Equation[
        [connect(port(ch_left,  :thermal_right, i), port(fuel, :thermal_left,  i)) for i in 1:n]...,
        [connect(port(ch_right, :thermal_left,  i), port(fuel, :thermal_right, i)) for i in 1:n]...,
    ]
    compose(System(connections, t; name=name), ch_left, ch_right, fuel)
end
```

**Python equivalent (`stream/composition/mtr_geometry.py:38-66`):**
```python
def plate(channel_l, channel_r, fuel):
    return CalculationGraph(DiGraph([
        (channel_l, fuel, vars_("T_left",  "h_left")),    # ch_l sends "T_left, h_left" — see ChannelAndContacts swap
        (channel_r, fuel, vars_("T_right", "h_right")),
        (fuel, channel_l, vars_("T_right",)),
        (fuel, channel_r, vars_("T_left",)),
    ]))
```

Python uses different mechanics — the `ChannelAndContacts.indices()` method (`stream/calculations/channel.py:510-515`) applies an internal swap so that the *graph-exposed* `h_left` of channel_l maps to its *internal* `h_right` slot, and vice versa. The net physical result is the same as Julia's direct wiring: channel_l's internally-named RIGHT wall is the one that exchanges heat with the fuel.

**Python's reference generator confirms the convention** (`test/generate_mtr_reference.py:306-307` comment, lines 317-323 extraction):
> "channel_L: thermally-connected wall = RIGHT (faces fuel plate); LEFT is adiabatic"
>
> ```python
> T_wall_right_l_sym = ch_l_state[ChannelVar.twall_right]   # connected
> T_wall_left_l_sym  = T_cool                                # adiabatic
> q_right_l_sym      = ch_l_state[ChannelVar.heatflux_right] # heat flowing
> q_left_l_sym       = [0.0] * NZ                            # adiabatic
> ```

## 2. The parity test bypasses the helper and wires the wrong face

`test/test_validation.jl:362-376` (the `mtr_symmetric` parity testset) does NOT call `plate(cac_l, cac_r, hd; name=...)`. It hand-builds the connections list:

```julia
conns = [
    # ... pump/hx connections ...
    [connect(getproperty(hd, Symbol(:thermal_left,  i)),
             getproperty(cac_l, Symbol(:thermal_left, i))) for i in 1:nz]...,   # ← WRONG
    [connect(getproperty(hd, Symbol(:thermal_right, i)),
             getproperty(cac_r, Symbol(:thermal_left, i))) for i in 1:nz]...,
    hd.power ~ 1e4,
]
```

Note line 371-372: `hd.thermal_left[i] ↔ cac_l.thermal_left[i]`. This wires fuel's LEFT face to channel_L's LEFT face. But geometrically channel_L's LEFT face is on the OUTSIDE (adiabatic), and channel_L's RIGHT face is the one touching the fuel.

Lines 542-545 (`mtr_asymmetric`) and 707-708 (`mtr_one_sided`) repeat the same mistake.

The right-channel wiring on line 374 happens to match Python (`ch_r.thermal_left ↔ fuel.thermal_right`), which is why right-channel parity rows are CLEAN. The disagreement is concentrated entirely on the LEFT channel.

## 3. Smoking-gun parity rows reflect the test bug, not a library bug

From `test/data/parity_report.csv` (latest, regenerated by Plan 58-02):

| Quantity | Julia (test wiring) | Python (correct via helper) | Tier |
|----------|---------------------|------------------------------|------|
| `mtr_symmetric.q_left_l[1]`        | 1.19e5  (Julia thinks LEFT face heated) | 0.0 (Python: LEFT adiabatic)   | FAIL |
| `mtr_symmetric.q_right_l[1]`       | 0.0     (Julia: RIGHT adiabatic)         | 1.19e5 (Python: RIGHT heated) | FAIL |
| `mtr_symmetric.T_wall_left_l[1]`   | 320.14 K (hot — connected wall)         | 313.62 K (T_cool — adiabatic) | FAIL |
| `mtr_symmetric.T_wall_right_l[1]`  | 313.62 K (T_cool — adiabatic)           | 320.14 K (hot — connected)    | FAIL |
| `mtr_symmetric.q_left_r[1]`        | 1.19e5  | 1.19e5  | CLEAN |
| `mtr_symmetric.T_wall_left_r[1]`   | 320.14  | 320.14  | CLEAN |

**The numerical values themselves agree** — both report `q = 1.19e5` on the connected side and `T_wall = 320.14 K` on the connected side. The disagreement is purely about which side gets the **label** "left". Because the test wires channel_L's LEFT face to the fuel, Julia's parity readback labels the connected wall "T_wall_left"; Python's reference labels it "T_wall_right".

The 92 FAIL rows decompose:
- 32 sym + 40 asym + 20 one-sided = 92 total
- Of those, 60 are q_*_l / T_wall_*_l rows on the LEFT channel
- The remaining 32 are tracking errors that fall out of the L/R-swapped-state propagating through the steady solve (the asymmetric T_wall values stop matching once the Python solve has heat coming in from the "right" side and Julia from the "left", because the channel sees the wrong H-on-which-side and the steady T distribution differs by a few %)

## 4. Three remediation options

### R-1 — Fix the test (RECOMMENDED)

Replace the hand-wired connections in `test/test_validation.jl` with `plate()` / `one_sided_connection()` helper calls **OR** swap `cac_l.thermal_left` → `cac_l.thermal_right` in the three test sites.

**Lines to change:**
- `test/test_validation.jl:371-372` (mtr_symmetric)
- `test/test_validation.jl:542-543` (mtr_asymmetric)
- `test/test_validation.jl:707-708` (mtr_one_sided)

Two equivalent ways to express the fix:

**(a) Use the helper directly** (cleanest, also exercises `plate()` in tests):
```julia
# Replace the hand-wired thermal connects with:
plate_sys = plate(cac_l, cac_r, hd; name=:plate_int)
# ... and rebuild conns/sys to wrap inside plate_sys, e.g. via compose_systems
```

**(b) Minimal-diff fix** (preserve test structure, fix wiring only):
```julia
# 371-372 was:  thermal_left[i] ↔ cac_l.thermal_left[i]
# Change to:
[connect(getproperty(hd, Symbol(:thermal_left,  i)),
         getproperty(cac_l, Symbol(:thermal_right, i))) for i in 1:nz]...,
[connect(getproperty(hd, Symbol(:thermal_right, i)),
         getproperty(cac_r, Symbol(:thermal_left,  i))) for i in 1:nz]...,
```

The right-channel wiring on line 373-374 / 544-545 / etc. is already correct — only flip the left-channel side.

The same fix applies to `mtr_one_sided` lines 707-708 (`cac_l.thermal_left` → `cac_l.thermal_right`).

**Effort:** ~10 lines of Julia, three test sites, no library changes.
**Risk:** zero — the helpers, source code, and Python reference are all correct; we're aligning the test with them.
**Side effect:** all 92 MTR parity FAILs collapse. The asymmetric tier-FAILs that aren't pure label-swap should also collapse to GRAY/CLEAN once the LEFT-channel side gets correct heat flux.

### R-2 — Flip the helpers

Edit `src/composition/helpers.jl` so `symmetric_plate` / `plate` / `one_sided_connection` use `cac.thermal_left` (instead of `cac.thermal_right`) for the LEFT-channel-touching-plate wiring.

**Don't do this.** The helpers are CORRECT and match Python. Flipping them would:
- Break every existing caller that already understood the convention
- Diverge from Python's geometry semantics
- Move the bug from the test (small, isolated) into the library (broad, breaking change)

### R-3 — Re-derive the Python references with Julia's test-wiring convention

Edit `test/generate_mtr_reference.py` to extract from the channel's `twall_left` / `heatflux_left` slots (instead of `twall_right` / `heatflux_right`) so that the reference values match Julia's mis-wired test.

**Don't do this either.** It would document the test bug as the de-facto convention, propagating the wrong physics interpretation.

## 5. Recommendation

**Take R-1, minimal-diff form (option b).** It's a surgical 6-line edit (three test sites × two lines each) to `test/test_validation.jl`, leaves `src/composition/helpers.jl` untouched, leaves Python untouched, leaves `test/generate_mtr_reference.py` untouched, and brings the parity comparison into honest alignment between the two implementations.

After the fix, `bin/jl test/test_validation.jl` regenerates `test/data/parity_report.csv` and we expect:
- 92 MTR FAILs → 0 (all label-swap rows resolve)
- Any residual non-zero rtol on T_wall, h_tc, q in the GRAY-tier range falls out as documented physics drift

If R-1 reveals additional FAIL rows that aren't label-swap (e.g., real numerical drift on the asymmetric scenario), Plan 56-06 task 6 will name them in MILESTONES.md per Phase 56's success criterion 3.

## How this happened

`test/test_validation.jl` was authored during Phase 56-05 specifically as the parity harness. At that time the helpers in `src/composition/helpers.jl` were also recent (Phase 55, the composition rewrite). The Phase 56-05 author chose to hand-wire the MTR scenarios to keep the parity setup self-contained — but copy-pasted the right-channel-wiring pattern for the left channel, where it happens to be physically backwards. Phase 56-05 SUMMARY explicitly noted that the MTR scenarios were emitting `solver_error` sentinel rows (not real per-tier values) because of the unrelated MTK determinacy bug; Phase 58-02 fixed that determinacy bug, and the moment real numerical values started appearing in the CSV, this label-swap surfaced as 92 FAIL rows. The 56-PAUSE-CONTEXT.md table at line 79 ("MTR sym/asym/one-sided parity sentinels — Phase 58 fixes Yes") was technically right that Phase 58 unblocked the MTR solve; what it didn't predict was that the *parity comparison* would then surface this independent test-wiring bug.

Confidence: high. The Python reference generator's own comment at `test/generate_mtr_reference.py:306-307` explicitly states the convention, and Julia's `plate()` helper implements it correctly. Only the test bypass deviates.
