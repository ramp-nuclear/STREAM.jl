STREAM.Components — Module
STREAM.Components

The acausal MTK components a model is built from.

Every component is a function returning an uncompiled System and taking name as a keyword. Components state equations and consume their physics from HTC, Friction and LocalLoss.

  • Connectors. FlowPort carries pressure, mass flow and stream temperature; ThermalPort carries a wall temperature and a heat flow. HydraulicTwoPort is the shared shell behind every one-inlet, one-outlet component, and flow_relation builds a new one from its relation between pressure rise and flow.
  • Channels. Channel, ChannelHeatFlux and ChannelAndContacts share a finite-volume core and differ in how heat arrives: a given coefficient, a prescribed flux, or per-cell thermal ports.
  • Hydraulics. Pump, Flapper, FrictionResistor, Resistor, VolumetricFlowResistor, LocalPressureDrop, Gravity, Inertia.
  • Solid heat. HeatDiffusion, a 2D finite-volume plate (Slab) or rod (Cylinder) with per-cell materials, contact conductances and optional axial conduction.
  • Neutronics. PointKinetics with any delayed group count, plus ReactivityController and the SCRAM callbacks.
  • Boundary conditions. HeatExchanger, ConstantTemperature, ConvectiveBoundary. HeatExchanger(T) holds a loop at T; given a UA it exchanges a finite amount of heat with a sink at T, and with a UA alone it couples two loops. A Channel wall or a ChannelHeatFlux flux needs no component: bind it in the connection list, ch.T_wall_left .~ T.
  • Loss of coolant. Tank, a free-surface inventory whose level sets the pressure at each connection; Environment, the ambient a break discharges into; and Orifice, the break itself, sealed until its machine opens it.

Base.Channel also exists, so using STREAM.Components leaves Channel ambiguous. Import it explicitly with using STREAM.Components: Channel, or qualify it.

A rod or an annulus for HeatDiffusion, with azimuthal symmetry: its mesh, its material and the contacts inside it. Radii starting at r = 0 make a solid rod, anything else an annulus.

STREAM.Components.ReactivityController — Type
ReactivityController(input_reactivity=nothing; machine=StateMachine())

The control reactivity a PointKinetics sees, read off a StateMachine.

input_reactivity(state, t_state, t) is every reactivity the control system inserts, given the state the machine is in, when it entered it, and the time now. That covers a postulated accident as well as the shutdown that answers it, so one function usually holds both:

machine = StateMachine()insertion(t) = t < 1.0 ? 0.002 * t : 0.002              # a rod withdrawal accidentscram(dt) = -0.06 * clamp(dt / 0.5, 0.0, 1.0)            # rods in over 0.5 srods = ReactivityController(machine=machine) do state, t_state, t    state === :SCRAM ? insertion(t) + scram(t - t_state) : insertion(t)end@named pk = PointKinetics(rods)machine.transitions = [(:NORMAL => :SCRAM, pk.P_neutron > 1.2e6, "high power")]

A trip on the kinetics is set after PointKinetics is built, since it reads pk. Leave machine out only for a controller whose state never changes. A controller is a StateSchedule under the name the kinetics use.

Arguments

  • input_reactivity: callable (state, t_state, t) -> Float64, the inserted reactivity. Without one there is none.

Keywords

  • machine: the StateMachine whose state is read. A fresh one in :NORMAL by default, reachable afterwards as rods.machine.

Returns

A callable rods(t) -> Float64, dimensionless.

STREAM.Components.Slab — Type
Slab(; x, z, y, material, x_contacts=Inf, z_contacts=Inf)

A plate for HeatDiffusion: its mesh, its material and the contacts inside it. x runs into the plate, through its thickness, and z runs along it, in the direction of the flow. y is the third direction, across which nothing is told apart: temperature, power and the coolant beside the plate are all single valued along it. For an MTR plate with 1D flow, y is the plate width spanning the channel.

Arguments

  • x: the nx + 1 cell boundaries through the plate [m]. A uniform mesh is Lx .* (0:nx) ./ nx, which stays symbolic for a design knob.
  • z: the nz + 1 cell boundaries along the plate [m]
  • y: length of the plate along y [m], Python's y_length
  • material: a Solid, or an nz × nx matrix of them for a clad plate
  • x_contacts: contact conductance [W/(m²K)] on the faces normal to x, anything that broadcasts to nz × (nx+1). Inf is perfect contact. A row such as [Inf 5e3 Inf Inf] puts a gap on one interface along the whole length.
  • z_contacts: the same for the faces normal to z, broadcasting to (nz+1) × nx

Returns

A Slab.

Throws

DimensionMismatch when a material matrix does not have one entry per cell.

STREAM.Components.StateMachine — Type
StateMachine(edges...; initial_state=:NORMAL, initial_time=0.0, abort_states=())

A control system, such as a reactor protection system: the state it is in, when it entered that state, a log of every state it entered and why, and the transitions it can take.

Hand the machine to whatever acts on its state, such as a ReactivityController, a Flapper or a DecayHeatSource, then set its transitions, and machine_callbacks turns them into events for the solver. See Trip a reactor or open a valve for worked recipes, and Events and control for how the solver finds an event.

A transition is (from => to, condition, description). from is one state, a collection of states, or nothing for any state. The description is what the log records as the cause; without one, the condition is written out.

The condition is one of:

  • An inequality between two expressions of the model, such as pump.inlet.ṁ < 0.01. It fires when it becomes true.
  • An equation such as ch.T[5] ~ 95.0. It fires when the two sides cross, either way.
  • A predicate (machine, sys, t) -> Real, positive where its condition holds, for what the other two cannot say, such as time in the current state: t - m.t_state - 2.0. sys[var] reads any variable of the model, and min and max combine conditions as "and" and "or". The solver calls it between its steps as well as at them, so it must have no side effects.

Each fires at the instant its condition becomes true. A condition that already holds fires when the machine enters a state its transition leaves from, and at the start of the run. When two fire at once, the one added first is taken. Entering a state in abort_states stops the integration.

Transitions can be set as soon as the components they mention exist: pump.inlet.ṁ is the same variable after mtkcompile. Assigning machine.transitions replaces the list and push!(machine, edge) adds to it, either before machine_callbacks reads it.

Arguments

  • edges: the transitions, each (from => to, condition) or (from => to, condition, description)

Keywords

  • initial_state: the state it starts in (default :NORMAL)
  • initial_time: when it entered that state [s] (default 0.0)
  • abort_states: states whose entry stops the integration (default none)

Fields

  • transitions::Vector{Transition}: the edges
  • state: the state it is in now
  • t_state::Float64: when it entered that state [s]
  • log: every state entered, oldest first, as (state, t, cause) named tuples in a MachineLog, which prints as a table. cause is the description of the transition taken, "initial" for the first entry, or whatever trip! was given.
  • abort_states::Set: the states that stop the integration

Throws

  • ArgumentError: for an edge whose condition is not one of the three forms

Examples

A machine set to scram ten seconds into a run, tripped by hand before then. It prints its state, its transitions and its log:

julia> machine = Components.StateMachine((:NORMAL => :SCRAM, (m, sys, t) -> t - 10.0, "ten seconds at power"));julia> Components.trip!(machine, 2.5; cause="low flow");julia> machineStateMachine in SCRAM since t = 2.5 s  transitions:    NORMAL → SCRAM when a predicate holds: ten seconds at power  log:    t = 0.0 s   NORMAL   initial    t = 2.5 s   SCRAM    low flowjulia> machine.log2 states entered:  t = 0.0 s   NORMAL   initial  t = 2.5 s   SCRAM    low flow

A machine with no transitions yet, which stops the run when it enters :UNCOVERED:

julia> Components.StateMachine(; initial_state=:OPEN, abort_states=(:UNCOVERED,))StateMachine in OPEN since t = 0.0 s  no transitions  stops on entering UNCOVERED  log:    t = 0.0 s   OPEN   initial

STREAM.Components.StateSchedule — Type
StateSchedule(f=nothing; machine=StateMachine())

A signal read off a StateMachine: f(state, t_state, t), called as s(t).

f gets the state the machine was in at t, the time it entered that state, and t, so a signal can follow how long the machine has been in a state: rods driving in after a scram, or a pump coasting down after a trip. ReactivityController is this under the name the kinetics use. Without an f the signal is zero.

The state is looked up in the machine's log, so s(t) is right for any t after the solve as well as during it. That is what makes a quantity computed from a schedule, such as sol[pk.reactivity], show the rods out before a scram and in after it.

Arguments

  • f: callable (state, t_state, t), returning what the component reading it expects

Keywords

  • machine: the machine whose state is read, a fresh one by default

Fields

  • f: the schedule
  • machine::StateMachine: the machine it follows

Returns

A callable s(t).

Examples

Rods worth 0.05 that drive in over 2 s after a scram at 10 s:

julia> machine = Components.StateMachine();julia> rods = Components.StateSchedule((state, t_state, t) -> state === :SCRAM ? -0.05 * min(t - t_state, 2.0) / 2.0 : 0.0; machine)StateSchedule on StateMachine(NORMAL since t = 0.0 s)julia> Components.trip!(machine, 10.0);julia> rods(5.0), rods(11.0), rods(20.0)(0.0, -0.025, -0.05)

STREAM.Components.Channel — Method
Channel(; name, n, geometry, g=0.0, h=0.0, darcy=Blasius(), liquid=H2O) -> System

Single-phase convective channel with n axial finite-volume cells, heated through a given convective coefficient against a wall temperature the caller binds.

The channel has one face per heated wall of its duct, named after the wall: left and right for a rectangle, outer for a circle. Each face passes h · heated · dz · (T_wall - T) into a cell, heated being the face's heated width.

Arguments

  • name: system name (Symbol)
  • n: number of axial cells (Int)
  • geometry: the channel's Duct
  • g: gravitational acceleration [m/s^2], 0.0 for horizontal (default 0.0)
  • h: convective coefficient [W/(m^2·K)], for every face or per face as a named tuple such as (left=5000.0,), where a face left out gets 0, adiabatic. Each value is a number, a length-n profile, or a function of time. A function becomes a callable parameter, which an operating point or overrides can replace with another function of the same type: ch.h_fn => fn for one function on every face, or ch.h_left_fn => fn for one given by face. Default 0.0, adiabatic.
  • darcy: wall friction model (AbstractDarcyFactor), default Blasius. Handed (T_wall, T_bulk, ṁ, liquid, geometry) per cell, with the mean of the faces' wall temperatures. Regime switching and the heated-wall viscosity correction are Friction.RegimeDependent.
  • liquid: coolant (AbstractLiquid), default H2O. Pass a Liquid to drive the energy balance, friction, and dimensionless observables with fixed properties.

External-input variables

  • T_wall_<face>(t)[1:n]: the face's per-cell wall temperature [°C], such as T_wall_left

These have no internal equation. A face with a nonzero h needs its wall closed, and so does any wall a friction model reads, such as Friction.RegimeDependent with a viscosity correction. A face with h = 0 under a friction model that ignores the wall, the default, needs nothing: its wall temperature appears in no equation. Close a wall in the connection list, as in ch.T_wall_left .~ 100.0, with a number, a length-n profile, a parameter or any expression in t. See Bind a wall temperature or heat flux.

Ports

  • inlet, outlet – FlowPort (mass + momentum + stream T) No thermal ports: see the external-input variables above.

STREAM.Components.ChannelAndContacts — Method
ChannelAndContacts(; name, n, geometry, g=0.0, htc=DittusBoelter(), darcy=Blasius(),
                   liquid=H2O) -> System

Convective channel with a per-cell ThermalPort array on each face, for conjugate heat transfer (the variant that connects to HeatDiffusion). The channel has one face per heated wall of its duct, named after the wall, as for Channel. The htc model gives each cell of each face its h_tc, the wall temperature arrives through the thermal ports, and the heat into the cell is h_tc[i] * heated * dz * (T_wall - T[i]), heated being the face's heated width.

Arguments

  • name: system name (Symbol)
  • n: number of axial cells (Int)
  • geometry: the channel's Duct
  • g: gravitational acceleration [m/s^2], 0.0 for horizontal (default 0.0)
  • htc: wall heat transfer model (HTC), default DittusBoelter. It is handed (T_wall, T_bulk, ṁ, liquid, geometry, P) per cell and returns h. Subcooled boiling is a model like any other: wrap one in SubcooledBoiling. Regime switching is HTC.RegimeDependent.
  • darcy: wall friction model (AbstractDarcyFactor), default Blasius. Handed (T_wall, T_bulk, ṁ, liquid, geometry) per cell, with the mean of the faces' wall temperatures. Regime switching and the heated-wall viscosity correction are Friction.RegimeDependent.
  • liquid: coolant (AbstractLiquid), default H2O. It drives the energy balance, friction, the HTC model, and the dimensionless observables.

Ports

  • inlet, outlet – FlowPort
  • thermal_<face>[1:n] – a ThermalPort array per face, one port per axial cell, such as thermal_left

STREAM.Components.ConstantTemperature — Method
ConstantTemperature(T; n, name) -> System

Fixed-temperature thermal boundary with n ports, one per cell. It absorbs or supplies whatever heat keeps each port at its temperature.

A port has to be connected to something that can carry its heat flow Q: MTK sets the flow of a port no connect touches to zero, so binding port.T directly on a heated wall would over-determine it. This component is that something.

Arguments

  • T: fixed temperature [°C], a number for every port or a length-n vector, one per port. Held as the parameter T_bc (a scalar or a vector), so remake can change it.
  • n: number of ports (default length(T) for a vector, 1 for a number)
  • name: system name (Symbol)

Ports

  • thermal1 … thermaln – ThermalPorts, named like a channel's per-cell faces so face, faces and port reach them as :thermal

Returns

Uncompiled System.

Example

@named wall = ConstantTemperature(100.0; n=4)conns = [..., faces((wall, :thermal) => (cac, :thermal_left))]

Throws

DimensionMismatch when a vector T does not have length n.

STREAM.Components.ConvectiveBoundary — Method
ConvectiveBoundary(; name, area) -> System

One-way convective heat sink at a single wall cell: imposes thermal.Q ~ h * area * (thermal.T - T_fluid). The conductance h and fluid temperature T_fluid are unbound input variables: supply them with binding equations to a channel's live h_tc[i] and coolant T[i]. The heat absorbed leaves through this element and is never returned to whatever supplies h/T_fluid, so the coupling is one-way.

This is the far-face element of single_channel: it cools a fuel plate's unconnected face using an adjacent channel's conditions without modelling a second channel (the equivalent-twin reduction). Used per axial cell; not a standalone loop component.

Arguments

  • name: system name (Symbol; supplied by @named).
  • area: heat-transfer area for the cell [m^2], e.g. geometry.heated[side] * dz.

Ports

  • thermal – ThermalPort; connect to the fuel cell's far-face port.

Input variables (bind externally)

  • h(t): convective conductance [W/(m^2·K)].
  • T_fluid(t): bulk fluid temperature [°C].

STREAM.Components.Flapper — Method
Flapper(; name, f=1.0, area=1.0, open_rate=1.0, machine, open_state=:OPEN,
        open_fraction=nothing, dp_linear=1.0, liquid=H2O) -> System

Passive check valve. Shut, it passes no flow. Open, it is a quadratic resistor,

\[Δp = f \dot m |\dot m| / (2 ρ A^2),\]

and part way open it passes xi times that flow, where xi is the open fraction, 0 shut and 1 fully open.

The valve holds no setpoint. It is open while its StateMachine is in open_state and shut otherwise, and the machine's transitions decide when. See Trip a reactor or open a valve for how to set them, and to change a setpoint between runs.

Opening and closing both take 1/open_rate seconds, along the same curve: xi = r(y), with r(y) = 3y² − 2y³ rising smoothly from 0 to 1. y climbs at open_rate while the machine is in open_state and falls back at the same rate in any other state, so a valve closed part way through opening shuts from where it had reached. A machine that starts in open_state, StateMachine(; initial_state=:OPEN, initial_time=t0), opens from t0 with no transition at all.

A shut valve carries no flow, so it belongs in parallel with a branch that carries flow meanwhile. In series it would block the loop.

A flapper is an Orifice with the discharge coefficient 1/√f: the two share the flow law, the opening and the sealed state. They differ in role. A flapper sits inside a loop and moves flow between its paths; an orifice is where the loop loses its coolant.

Arguments

  • name: system name (Symbol), injected by @named
  • f: open-state quadratic loss coefficient (default 1.0)
  • area: flow area [m²] (default 1.0)
  • open_rate: how fast it opens and closes [1/s]; either takes 1/open_rate s (default 1.0)
  • machine: the StateMachine the valve follows (default a fresh one in :CLOSED)
  • open_state: the state in which the valve is open (default :OPEN)
  • open_fraction: a function of time t -> xi in [0, 1] to use instead of the ramp above, such as an interpolation of a measured opening curve. It may read the machine but not the model's variables: a fraction that depends on the flow it controls makes the equations non-smooth, and a steady solve stalls. Zero or less means shut.
  • dp_linear: pressure drop [Pa] below which the open valve's flow goes as ΔP instead of its square root (default 1). The open valve passes ṁ = xi·area·sqrt(2ρ/f)·ΔP / (ΔP² + dp_linear²)^{1/4}, which crosses zero with a finite slope. Well above dp_linear this is the quadratic law above.
  • liquid: coolant (AbstractLiquid), default H2O, whose density on the side the flow enters sets the open valve's pressure drop

Ports

  • inlet, outlet: FlowPort (pressure, mass flow, temperature)

Returns

Uncompiled System, with the open fraction as the variable xi.

STREAM.Components.FlowPort — Method
FlowPort(; name, p=1.0e5, ṁ=FLOW_START, T=T_ROOM)

Acausal hydraulic connector. p is the across (potential) variable, ṁ is the flow variable (sums to zero at a junction), and T is a stream variable carried with the flow.

In a connection set the pressure is equalised across every port, the mass flows sum to zero, and the temperature is neither: it follows the flow direction. See HydraulicTwoPort for how instream resolves a stream variable.

The @connector function form lets the initial values double as keyword arguments, so a port can be built already seeded.

Arguments

  • name: connector name (Symbol; supplied by @named).
  • p: total pressure [Pa], the static pressure plus the dynamic head ρv²/2. Equal pressures at a junction therefore carry Bernoulli's drop into a narrower part, and a local loss is a loss of total pressure. Saturation depends on the static pressure, which a channel works out for itself.
  • ṁ: mass flow rate [kg/s]; positive points into the port. A component builds a port its flow normally leaves by with -FLOW_START.
  • T: temperature [°C].

STREAM.Components.HeatDiffusion — Method
HeatDiffusion(body; name, axial=false, power_shape=nothing, power=nothing,
              T0=T_ROOM) -> System

Heat conduction in a Slab or a Cylinder on its 2D finite-volume mesh. This is Python STREAM's Fuel. Heat conduction in fuel derives the equations, and Model a clad plate or a fuel rod shows how to build either.

Each cell balances its heat content against conduction through its faces and its share of the power:

\[ρ c_p V dT/dt = \sum_f A_f (T_f - T) / R_f + P s\]

where T_f is the temperature on the far side of face f and R_f the resistance per unit area between the two: half of each cell's width over its conductivity, plus the face's contact resistance 1/h. An outer face conducts to the temperature on its port over half a cell. Conduction across x is always on, and along z with axial=true.

Arguments

  • body: a Slab or a Cylinder
  • name: system name (Symbol)
  • axial: conduct along z as well (default false, each axial slice independent)
  • power_shape: s, the fraction of power in each cell, an nz × nx matrix used as given, so cladding cells hold zero. The default nothing is a uniform power density, each cell's share being its volume over the body's.
  • power: P, the total power [W]. A number makes it the parameter power, which remake can change. nothing (the default) makes it an unknown the caller binds, such as rods.fuel.power ~ pk.P * power_scale for a plate driven by point kinetics.
  • T0: initial temperature of every cell [°C]

Ports

STREAM.Components.HeatExchanger — Method
HeatExchanger(T_bc; UA=nothing, liquid=H2O, name) -> System

A heat exchanger to a sink held at T_bc: the cooling a loop gets from something outside the model, such as a cooling tower, a pond or the air.

With no UA, the default, the exchanger is ideal. Liquid leaves at T_bc whatever arrives, in either flow direction, so the sink takes any heat the loop brings it.

With a UA, the sink is still at a fixed temperature but the exchange is finite. The liquid's capacity rate $C = |\dot m| c_p(T_{in})$ [W/K] is the heat it carries per kelvin of temperature change. The sink's capacity rate is unbounded, since it stays at T_bc however much heat it takes, so C is the smaller of the two and the effectiveness is $1 - e^{-UA/C}$:

\[T_{out} = T_{in} + (1 - e^{-UA / C}) (T_{bc} - T_{in})\]

As UA grows this tends to the ideal exchanger, T_out = T_bc. As the flow stops, C goes to zero and so does the heat removed, Q = C (T_out - T_in). Use the two-stream method to model the sink's own flow. Both forms have no pressure drop: put a resistor in series for one. See Heat exchangers and the heat sink.

Arguments

  • T_bc: sink temperature [°C], the parameter T_bc
  • UA: overall conductance [W/K]. nothing gives the ideal exchanger. A number is held as the parameter UA. A function (ṁ) -> UA of the mass flow makes it the unknown UA_eff.
  • liquid: the coolant, for its specific heat (default H2O); unused when ideal
  • name: system name (Symbol)

Ports

  • inlet, outlet: FlowPort (pressure, mass flow, temperature)

Returns

Uncompiled System. With a UA it has the observed Q, the heat the liquid takes up [W], negative when the sink cools it.

STREAM.Components.HeatExchanger — Method
HeatExchanger(; UA, arrangement=HTC.Counterflow(), primary_liquid=H2O,
              secondary_liquid=H2O, name) -> System

A heat exchanger between two flowing streams, the primary and the secondary, solved by the effectiveness-NTU method. Each side is a two-port with no pressure drop, reached as hx.primary and hx.secondary, so it sits in a loop like any other component: inseries(pump, hx.primary, core).

The exchanger stores no heat: the outlets follow the inlets at once. With capacity rates $C = |\dot m| c_p(T_{in})$ on each side, the heat each stream carries per kelvin,

\[Q = ε C_{min} (T_{s,in} - T_{p,in}), \qquad ε = ε(NTU, C_r), \quad NTU = UA / C_{min}, \quad C_r = C_{min} / C_{max}\]

where Q is the heat into the primary, and each outlet is its inlet plus Q over its own capacity rate. HTC.effectiveness gives ε for the arrangement. When exactly one side flows backwards, a counterflow unit runs as parallel flow and the reverse, and the model switches formulas to match. A side that stops flowing has $C \to 0$, so Q goes to zero: a loss of heat sink. See Heat exchangers and the heat sink.

  • arrangement: HTC.Counterflow() or HTC.ParallelFlow(), for forward flow on both sides
  • primary_liquid, secondary_liquid: the coolant on each side (default H2O)
  • name: system name (Symbol)

Ports

  • primary.inlet, primary.outlet, secondary.inlet, secondary.outlet: FlowPorts

Returns

Uncompiled System. The observed Q is the heat into the primary [W], negative when the primary is the hot side. Each side has T_in (the temperature arriving, whichever way it flows), C and ΔT, the rise from its inlet to its outlet.

STREAM.Components.HydraulicTwoPort — Method
HydraulicTwoPort(; name) -> System

Shared shell for a hydraulic two-port component: one inlet and one outlet FlowPort, with mass conservation and temperature pass-through, so each component only has to state its own law. The shell observes the two quantities a law relates: Δp, the pressure rise outlet.p - inlet.p, as Python STREAM's dp_out, and ṁ, the flow in at the inlet. A component states its relation between them and hands it to flow_relation:

function Resistor(R; name)    two = HydraulicTwoPort(; name)    @unpack Δp, ṁ = two    @parameters R = R    return flow_relation(two, [Δp ~ -R * ṁ])end

sol[ssys.r.Δp] then reads the pressure change of any two-port. The outlet's flow starts negative and the inlet's positive, so a steady solve starts the component flowing forward.

A two-port component takes flow in at one port and passes it out at one other, holds no fluid, and adds no heat. Pump, Flapper, Resistor, FrictionResistor, VolumetricFlowResistor, LocalPressureDrop, Gravity and Inertia are built on it. Channels are not two-ports: they hold fluid and exchange heat, and state their own energy balance. inseries and inparallel accept either, needing only an inlet and an outlet.

The component's law is usually one equation for Δp. Besides defining Δp and ṁ, the shell holds three more:

inlet.ṁ + outlet.ṁ ~ 0        # what goes in comes outoutlet.T ~ instream(inlet.T)  # forward flow: outlet carries the inlet streaminlet.T ~ instream(outlet.T)  # reversed flow: inlet carries the outlet stream

On instream

T on a FlowPort is declared [connect = Stream], making it a stream variable: carried along by the flow rather than equalised across a connection. instream(inlet.T) is the temperature of the fluid arriving at inlet from whatever is connected there, mixed if several branches feed it. Plain inlet.T is the opposite direction, the temperature this component sends back out through that port. The two equations above therefore say that whatever arrives at one port leaves at the other, once per flow direction.

outlet.T ~ inlet.T is not equivalent: it relates the two outgoing values and leaves the incoming ones unconstrained.

Stream connectors come from Modelica. The reference for the semantics is Franke et al., "Stream Connectors: An Extension of Modelica for Device-Oriented Modeling of Convective Transport Phenomena", Modelica Conference 2009.

Arguments

  • name: the component's name, the same one it builds its own System under

Returns

An uncompiled System holding inlet and outlet and observing Δp and ṁ.

STREAM.Components.Orifice — Method
Orifice(; name, area, cd, machine, open_state=:OPEN, open_rate=10.0, dp_linear=1.0,
        cc=nothing, liquid=H2O) -> System

A hole a liquid discharges through: a break in a pool wall, a breach in a pipe, or a severed pipe end. Open, it passes

\[\dot m = C_d A \sqrt{2 ρ Δp}\]

with Δp the pressure across it. Loss of coolant derives it, and Model a break shows a break, a siphon breaker and the cavitation check in use. Close to Δp = 0 the flow goes as Δp instead (see dp_linear), so it passes through zero smoothly and reverses when Δp does. What kind of break it is depends on where it sits in the loop, not on what it computes: discharge into an Environment to lose the inventory.

Shut, it passes no flow and leaves the pressure across it free, so the intact loop solves with the break already in place. It opens and shuts with its StateMachine exactly as a Flapper does, over 1/open_rate seconds along the same curve:

# A break at t = 100 s.@named breach = Orifice(; area=5e-4, cd=discharge_cd(:sharp),                        machine=StateMachine(; initial_state=:OPEN, initial_time=100.0))# A siphon breaker: the drain line shuts for good once the pool falls to z_breaker.line = StateMachine(; initial_state=:OPEN)@named drain = Orifice(; area=5e-4, cd=0.6, machine=line)line.transitions = [(:OPEN => :SHUT, pool.L < z_breaker, "siphon breaker")]

The orifice applies the single-phase law throughout and does not check, during the run, whether the liquid at its throat flashes. With a contraction coefficient cc it reports the static pressure at its vena contracta and how far the liquid there is below saturation. cavitation reads those after the run, at the saved times only, so a dip below saturation between two saved times goes unseen. To catch one as it happens, put a transition on the subcooling in a StateMachine:

flash = StateMachine(; initial_state=:LIQUID)push!(flash, (:LIQUID => :FLASHING, breach.subcooling < 0, "throat at saturation"))

Arguments

  • name: system name (Symbol), injected by @named
  • area: geometric area of the hole [m²]
  • cd: discharge coefficient, a number such as discharge_cd(:sharp), or a function of the throat Reynolds number such as Re -> lichtarowicz_cd(Re, 2.0). The Reynolds number is taken on the diameter of a round hole of that area and floored at 1. At zero flow, through a shut break or one just opening, the floor keeps such a cd positive, so a break opening from rest starts to flow.
  • machine: the StateMachine the break follows (default a fresh one in :SHUT, which never opens)
  • open_state: the state in which the break is open (default :OPEN)
  • open_rate: how fast it opens and shuts [1/s] (default 10)
  • dp_linear: pressure difference [Pa] below which the flow goes as Δp instead of its square root (default 1). The open orifice passes ṁ = xi·cd·area·sqrt(2ρ)·Δp / (Δp² + dp_linear²)^{1/4}, which crosses zero with a finite slope. Well above dp_linear this is the square-root law above.
  • cc: contraction coefficient of the vena contracta, or nothing (default) to skip the throat report
  • liquid: coolant (AbstractLiquid), default H2O

Ports

  • inlet, outlet: FlowPort

Returns

Uncompiled System, with the open fraction as the variable xi, and with cc given the throat pressure p_throat [Pa] and the throat subcooling [K], the saturation temperature at p_throat less the liquid temperature.

STREAM.Components.PointKinetics — Method
PointKinetics(rho_c_fn::Any; name, Lambda=U235_LAMBDA, beta_k=U235_BETA_K,
              lambda_k=U235_LAMBDA_K, temp_worth=nothing, ref_temp=nothing,
              power_input=nothing, P0=1.0) -> System

Keepin (1965) point kinetics with G delayed precursor groups, so 1 + G ODEs:

\[\begin{aligned} dP_n/dt &= (ρ - β)/Λ \, P_n + \sum_k λ_k C_k \\ dC_k/dt &= (β_k/Λ) \, P_n - λ_k C_k, \qquad k = 1, …, G \end{aligned}\]

with Pₙ the neutron power, the unknown P_neutron.

G is length(beta_k). The defaults are the six-group U-235 data (U235_BETA_K, U235_LAMBDA_K), giving seven equations. point_kinetics_steady_state gives the precursor concentrations that hold power steady at criticality.

The control reactivity comes from a callable rho_c_fn(t) (a ReactivityController is itself callable), and the total reactivity becomes

\[ρ = ρ_c(t) + \sum_j α_j (T_j - T_{ref,j})\]

where the sum is the per-cell temperature feedback. Each weight αⱼ is a temperature coefficient of reactivity (dρ/dT) and enters signed: a stabilizing reactor has a negative coefficient, so αⱼ is normally negative.

A critical reactor is rho_c_fn = t -> 0.0; a constant bias is t -> ρ₀.

The system starts where it was built to: rho_c_fn defaults to the callable given, and P_neutron and C to the critical steady state holding a total power P0, with power_input taken at t = 0, as point_kinetics_steady_state computes it. Put any of them in the operating point to start elsewhere.

The total power is

\[P = P_{neutron} + P_{input}(t)\]

where power_input is power fission does not produce, such as decay heat from a STREAM.DecayHeat.DecayHeatSource. Heat the fuel with P. A power trip may watch either: P_neutron is what a neutron flux monitor measures, P what the fuel receives. See Point kinetics and feedback for the physics.

Arguments

  • rho_c_fn (positional): callable (t) -> Float64, or a ReactivityController. Its concrete type is captured at construction.
  • name: system name (Symbol, injected by @named)
  • Lambda: neutron generation time [s] (default U235_LAMBDA)
  • beta_k, lambda_k: per-group delayed data; length(beta_k) sets the group count
  • temp_worth::Union{Nothing,Dict}=nothing: per-component feedback weights. Keys are uncompiled MTK Systems; values are scalar (broadcast to every cell), a length-n vector (Channel), or an nz×nx matrix (HeatDiffusion, flattened row-major as j = (jz-1)*nx + jx). nothing disables feedback.
  • ref_temp::Union{Nothing,Dict}=nothing: per-component reference temperatures [°C], same key structure. Missing keys default to zero, so the full temperature contributes.
  • power_input=nothing: non-fission power added to P_neutron. A Real becomes the parameter power_input, and anything else is taken as a callable (t) -> Float64 and becomes the callable parameter power_input_fn. Either carries the value given as its default, so neither has to appear in the operating point, and solve_transient can override either. nothing leaves P ~ P_neutron.
  • P0=1.0: the total power P the default initial state holds, in the units of P_neutron

Returns

Uncompiled System with unknowns P_neutron, C[1:G], P, and one T_source array per feedback component, plus the callable parameter rho_c_fn.

P is algebraic, so mtkcompile moves it to observed and the compiled system keeps 1 + G states. Read it off a solution as sol[ssys.pk.P].

Important: with temp_worth set, the T_source unknowns are free until temperature_feedback binds them; do that and compose before mtkcompile.

STREAM.Components.Tank — Method
Tank(; name, area, L0, ports, liquid=H2O, p_surface=ATM, T0=T_ROOM,
     fixed_temperature=true, volume=nothing, Q_ext=0.0, g=G_EARTH) -> System

A body of liquid with a free surface: a pool, or a tank with a cover gas. It holds an inventory whose level L is a state, and it sits in a loop as a node with any number of connections, each at its own elevation.

Each connection's pressure is the surface pressure plus the head of liquid above it,

\[p_{port} = p_{surface} + ρ(T) g (L - z)\]

so a leg's driving head falls as the tank drains, reaches zero when the surface comes down to the connection, and goes negative once it is above the surface. Liquid leaves through every port at the tank's temperature. A port the surface has fallen below keeps passing liquid under that negative head: the tank does not shut it. To stop the flow there, put an Orifice on the line with a transition that shuts it when L passes the port.

The level follows the net inflow, with each port's ṁ positive into the tank:

\[ρ A(L) dL/dt = \sum \dot m\]

Temperature

By default the temperature is held at T0, before and during the transient. The tank then takes in whatever heat the loop brings it without warming, which suits a pool whose heat-up is of no interest. With fixed_temperature=false, T follows the enthalpy the inflows bring,

\[ρ V(L) c_p dT/dt = \sum \max(\dot m, 0) c_p (T_{in} - T) + Q_{ext}\]

Outflow leaves at T, so it adds nothing. A port's instream temperature is what arrives if liquid flows in, whichever way it is flowing, so the balance picks the inflowing ports itself.

The steady solve

A level is the integral of the net flow, so on its own a steady state leaves it undetermined. While the parameter pinned is true, the default, the level is instead held at L0, which is what a steady solve needs. Release it for the transient:

sol_ss = solve_steady(ssys, guess)sol = solve_transient(ssys, sol_ss, times; overrides=[ssys.pool.pinned => false])

With the energy balance on, the steady temperature is the mix of the inflows, so a tank with no inflow in the steady state has nothing to set it. Start such a run from the declared state instead, solve_transient(ssys, [ssys.pool.pinned => false], times). Set up a tank for the steady solve shows each case, and Loss of coolant why they differ.

Events

Reaching a level is a StateMachine transition on L, such as (:INTACT => :CORE_UNCOVERED, pool.L < z_core_top, "core uncovered") with :CORE_UNCOVERED among the machine's abort_states to stop the run there.

Arguments

  • name: system name (Symbol), injected by @named
  • area: free-surface area [m²], a number or a function of level L -> A. A function needs volume.
  • L0: initial level, and the level held while pinned [m]
  • ports: connection elevations [m], in the datum of L, as a NamedTuple such as (suction=0.0, return=0.5). Each becomes a FlowPort of that name.
  • liquid: coolant (AbstractLiquid), default H2O
  • p_surface: pressure above the liquid [Pa] (default ATM)
  • T0: the held temperature, or the initial one with fixed_temperature=false [°C]
  • fixed_temperature: hold T at T0 (default true). false makes T follow the energy balance.
  • volume: liquid volume as a function of level L -> V [m³], consistent with area (dV/dL = A). Required with a level-dependent area; a constant area gives area·L.
  • Q_ext: heat into the liquid from outside the loop [W] (default 0). It only acts with fixed_temperature=false.
  • g: gravitational acceleration [m/s²] (default G_EARTH)

Ports

One FlowPort per entry of ports, named as in it. A port can start or end an inseries chain, inseries(pool.bottom, breach, ambient.port).

Returns

Uncompiled System with the level L, the temperature T, the inventory M = ρ·V(L) [kg], and the parameter pinned.

Throws

  • ArgumentError: for a tank with no ports, or a level-dependent area with no volume

  • power_input: the non-fission share of P0 [W] (default 0.0, so fission makes all of it)

Returns

STREAM.Components.reset! — Method
reset!(machine::StateMachine) -> StateMachine

Put machine back in the state and time it started from, and clear its log down to that first entry. Its transitions are kept.

A machine remembers what happened in the last run, so a second run from the same model, for instance after changing a setpoint with remake, needs the machine reset first.

Returns

The same machine.

STREAM.Components.trip! — Method
trip!(machine::StateMachine, t_now; state=:SCRAM, cause="manual") -> state

Put machine into state at time t_now, stamping t_state and adding cause to the log.

Taking a transition calls this with the transition's description. Calling it yourself is a manual override, which is what the default cause says. It latches: calling it again while the machine is already in state changes nothing, so the first time and cause stand.

Arguments

  • machine: the StateMachine to move
  • t_now: the time of the transition [s]

Keywords

  • state: the state to enter (default :SCRAM)
  • cause: why, as the log records it (default "manual")

Returns

The state the machine is in afterwards.
